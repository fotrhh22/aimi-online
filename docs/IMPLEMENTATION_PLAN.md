# AIMI 전체 앱 구현 계획

갱신: 2026-11-08. UX 기준은 PDF v18, 13슬라이드·35개 모바일 상태다. 전체 기능 구현이 목표이며 프롬프트 개선과 업무 기반 모델 추천의 실제 연동까지 포함한다. AI 호출은 후반에 연결하되 화면·계약·데이터·제작/발행 도구는 선행한다. 아래 순서는 이전 P0~P8 계획을 대체한다.

## 현재 출발점

초기 API/contracts, 실제 Supabase 초기 migration·런타임 역할·EP 원장/보상 거래, GitHub CI, Render 초기 배포는 구현 기록이 있다. 실제 미니앱은 홈 미리보기이며 토스 로그인·API 연결·게임·정원·소셜·AI 서비스는 완료되지 않았다. 인프라는 착수 때 기존 상태를 재확인하고 필요한 부분만 확장한다. 상세 상태는 IMPLEMENTATION_STATUS.md를 따른다.

공식 UI/UX·최종 산출물 인수는 TOSS_DELIVERY_AND_ACCEPTANCE.md를 따른다. Phase1 TDS 호환·Provider 적용/내비게이션·safe area 검증과 Phase12 .ait/서버/DB/실기기 기록을 완료 기준에 포함한다.

## 최신 결정과 단계별 의존성

- 시각 기준: PDF v18, 공통 UI는 UI_COMPONENT_CONTRACTS.md. 확정 UX를 임의 재설계하지 않는다.
- 게임: GAME_SCORING_AND_REWARDS.md. 만점/완주/보상 상한은 확정 방향, 100점과 구체 경제 수치는 개발 기본안/조정 대상이다. Dino 선행 불필요.
- 추천: RECOMMENDATION_POLICY.md. LLM은 업무/필수 기능/Small·Medium·High 분석, 코드는 검증 DB로 비용순 최대3개. P25/P50/P75는 초기 자체 품질 gate다.
- 제작: 별도 생성기는 사용자가 추후 개발하며 이번 목표 밖이다. 대표 상점/캐릭터 에셋과 목표·키워드·조건·결과 이미지의 예시 챌린지는 Codex가 PDF를 참고해 직접 준비·검증한다. 사용자가 샘플을 추가 제공하거나 생성기를 먼저 완성할 필요는 없다. 앱은 공유 Supabase의 승인 콘텐츠 계약/조회/일정 선택을 구현한다.
- 이미지 챌린지는 조건 ID 매칭·가중치·명시 감점·필수 조건·저/고 모델 임계값에 따른 서버 규칙 판정이다. 게임 중 생성/LLM 채점/임베딩 유사도 채점은 사용하지 않는다.

## 효율성과 실행 방식

첫 검증 흐름은 길 건너기이며 Dino는 추가 게임이다. 게임 엔진/SDK는 재사용하고 완성품 게임 repo를 기본 의존성으로 가져오지 않는다. 버전/라이선스/실기기 성능을 확인한다. 컴포넌트는 miniapp/src/ui에서 시작하며 필요 전 대형 공통 라이브러리를 만들지 않는다.

Phase3 이후 PDF 예시 에셋의 앱용 재구성, Phase0의 데이터 계약 후 모델 수집은 다른 작업과 독립 진행 가능하다. 승인 콘텐츠 계약/개발 fixture는 Phase3, 콘텐츠 연동 인수는 Phase11로 구분한다. 생성기 개발 완료를 앱 코드 구현의 선행 조건으로 두지 않는다. 초기에는 PDF 예시 에셋과 개발 과제 묶음으로 검증하며 대량 생성은 이번 목표에 포함하지 않는다.

게임 엔진 실기기 검증·애니메이션 제작·이미지 조합 커버리지·AA 접근/매핑·토스 설정이 주요 불확실성이다. 일정은 이들의 대표 사례를 확인한 뒤 추정한다. 모든 Phase는 필요한 검증을 포함하고 Phase12는 최종 연결 검증이다.

## Chrome Dino형 구현안

- AIMI 캐릭터가 달리는 횡스크롤 2D 게임, 탭 점프. 숙이기/이중 점프는 현재 범위에 추가하지 않는다.
- 고정 simulation tick·시드 기반 장애물/수집물 생성. 현재 속도·점프 곡선·착지 시간을 고려해 통과 가능한 패턴만 생성한다.
- 이동 거리 점수·수집 EP 분리, 속도 상한/EP 상한/예산 산식은 game_version 정책. 수치는 실기기 검증으로 조정한다.
- 캐릭터는 동일한 판정 크기·이동 성능, 서로 다른 시각 offset/스프라이트만 사용. 정원용 정지 이미지와 달리 달리기·점프·피격 프레임을 준비한다.
- 서버 발급 play_id/seed/version으로 시작. 입력 tick 로그와 결과를 제출해 서버가 같은 순수 simulation 규칙으로 재계산하고 시간·이벤트 상한을 검증한다. 이것만으로 모든 클라이언트 조작을 차단한다고 주장하지 않는다.
- 백그라운드 이동 시 정지, 동일 세션 복구. 완료 멱등성·응답 유실 재조회·자정 시작일 귀속을 공통 game-core가 처리한다.
- 외부 코드·에셋은 라이선스/출처를 확인하며 AIMI 에셋으로 제작한다. 엔진 버전은 WebView 입력·프레임·메모리 검증 후 고정한다.

## 작업 위치 (아래 신규 경로는 구현 예정)

- apps/miniapp/src/ui/: 토큰 의존 공통 UI와 상태 조합 예제.
- apps/miniapp/src/features/: home, mission, optimizer, recommendation, garden, shop, social 화면.
- apps/miniapp/src/games/: 공통 React/엔진 연결, Dino/길 건너기/러너 장면.
- packages/game-core/: 렌더러와 분리된 순수 게임 규칙·시드·검증 코드. workspace 등록 필요.
- packages/contracts/: API·게임 이벤트·에셋·콘텐츠·taskProfile 스키마.
- apps/api/: 인증·경제·일정 조회·게임 검증·판정·구매·친구·AI 작업.
- content/: 승인/초안 manifest, 일정, 상품·캐릭터 정의. 비밀과 비공개 원본은 공개 저장소에 넣지 않는다.
- 외부 생성기: 이번 폴더 생성/구현 대상 아님. 데이터 계약은 packages/contracts/src/content에서 관리.
- tools/model-sync/, .github/workflows/: 자료 수집·검증·스냅샷 발행.

## 완료 원칙

각 단계는 코드·적절한 검증·상태 문서 갱신까지 포함한다. 목업·실제 개발 DB·토스 샌드박스·운영을 구분한다. LLM 평가 기준은 LLM_WORKFLOWS.md, 거래·판정·동시성 규칙은 DEVELOPMENT_SPEC.md를 따른다. 비밀 키는 서버/Actions secrets에만 둔다. 배포·외부 생성은 세션의 사용자 승인 범위를 따른다.

## v1 실행 결과 · 2026-11-09

사용자의 최신 goal에서는 자동 수집Actions·생성기·외부 SQL/콘솔/배포·사용자 실기기를 제외했다. 해당 작업은 위 운영 전체 계획의 후속 범위다. 로컬 v1 실제 구현/검증은 IMPLEMENTATION_STATUS.md 상단과 PROTOTYPE_V1.md를 따른다. Phase0~12 운영 출시 완료와 로컬 v1 완성을 혼동하지 않는다.
