## 1. 서비스 정의

게임으로 얻은 자원 안에서 목표 이미지에 필요한 키워드와 모델을 선택하는 프롬프트 챌린지, 사용자가 입력한 질문을 다듬고 모델 선택을 학습하는 프롬프트 개선기, EP로 꾸미고 친구에게 보여주는 정원을 제공한다.

학습의 중심은 무조건 짧은 질문이나 저성능 모델을 권장하는 것이 아니다. 목표를 달성하는 데 필요한 조건을 선택하고, 조건의 구체성과 모델 성능 사이에서 자원을 배분하는 경험을 제공한다.

기존 오프라인 이미지 생성·자전거 발전·열전사 영수증 캠페인과는 별도 서비스다. 기존 캠페인 저장소와 동작을 이번 개발로 변경하지 않는다.

## 2. 1차 범위와 제외 사항

### 확정 범위

1. 일일 액션 게임과 이미지 프롬프트 챌린지.
2. 프롬프트 개선 및 모델 추천·사용량 시뮬레이션.
3. 출석·팁 확인·개선기 체험 등 일일 보상.
4. EP를 이용한 정원 꾸미기와 게임 캐릭터·맵 테마 구매.
5. 친구 추가, 친구 정원 방문, 챌린지 달성 상태 공유.
6. 앱인토스 로그인과 미니앱 내 완결된 이용 흐름.

### 제외 사항

- Chrome 확장 프로그램 및 외부 채팅 사용량·토큰 수집·연동 API.
- HealthKit, Health Connect, 운동 측정, 건강 기록, 수동 운동 입력, OCR.
- 일일·절약 영수증, 열전사 출력, 자전거 발전 연동.
- 자유 게시판, 채팅, 순위 경쟁, 실시간 멀티플레이.
- 현금성 보상, EP 환전, EP를 이용한 도전 횟수·게임 예산 구매.
- 플레이어 제출마다 실행하는 이미지 생성 및 실시간 CLIP 서버.
- 글·동영상 목표 과제. 추후 별도 평가 체계를 가진 확장 유형으로만 검토한다.

## 3. 주요 사용자 흐름

토스 로그인 → 홈 → 오늘의 목표 이미지·규칙 확인 → 오늘의 액션 게임 플레이 → 기록에 따른 게임 예산 확보 및 코인 EP 획득 → 키워드와 모델 선택 → 자동 조합 문장 미리보기 → 제출 → 사전 생성 결과 이미지·점수·통과 여부·피드백 확인 → 성공 EP 수령 → 정원·캐릭터·맵 테마 꾸미기 → 친구 정원 방문.

프롬프트 개선기는 게임과 별개로 홈에서 진입할 수 있다. 개선기를 사용하지 않아도 게임과 정원을 이용할 수 있다.

## 4. 화면 구성

**제안:** 하단 탭은 `홈 / 미션 / 정원 / 마이`의 네 개로 구성한다. 개선기와 소셜은 각각 홈·정원에서 진입한다.

| 화면 | 표시 내용 | 주요 동작·상태 |
|---|---|---|
| 시작·로그인 | 서비스 소개, 토스 로그인 | 로그인·재접속·실패 안내 |
| 홈 | EP 잔액, 출석, 오늘의 게임·챌린지 상태, 랜덤 팁, 개선기 진입 | 보상은 서버 확인 후 반영 |
| 오늘의 미션 | 오늘의 목표 이미지, 액션 게임, 각각 남은 도전 횟수, 보상 설명 | 게임 시작·프롬프트 조합 진입 |
| 게임 안내 | 조작, 기록 기준, 코인과 예산의 차이 | 준비 완료 후 플레이 |
| 게임 플레이 | 현재 기록, 수집 코인, 종료·중단 | 일시 정지·앱 이탈 처리 |
| 게임 결과 | 이번 기록, 예산 산정 내역, 코인 EP, 남은 게임 횟수 | 재도전·프롬프트 조합 |
| 키워드·모델 조합 | 목표 이미지 재확인, 카드 범주·비용, 선택 순서, 모델 선택, 총비용·잔액·문장 미리보기 | 선택·해제·순서 변경·제출 |
| 챌린지 결과 | 대응 결과 이미지, 점수, 선택 모델의 통과 기준, 필수 조건, 성공·실패 이유, 관련 팁 | 성공 보상 확인·재도전 |
| 프롬프트 개선 입력 | 사용자 원문, 일일 잔여 호출량 | 명시적 개선 요청 |
| 개선 결과·모델 시뮬레이션 | 원문과 수정안, 수정 이유, 모델 추천, 비용·사용량 가정 | 수정안 편집·복사·원문 복원 |
| 내 정원 | 식물·장식·배경·캐릭터, EP 잔액 | 편집·상점·친구 방문 |
| 상점·보관함 | 정원 아이템, 게임 캐릭터, 맵 테마 | 구매 확인·배치·장착 |
| 친구 목록·정원 | 친구 코드·초대, 친구 정원과 공개된 달성 상태 | 수락·방문·정해진 반응 |
| 마이 | 이용 기록, 데이터·공개 설정, 계정 관리, 도움말 | 설정 변경·계정 관련 처리 |

화면 수는 구현 시 합칠 수 있지만 입력·결과·에러 상태는 생략하지 않는다. 목표 이미지는 시작 전과 최종 조합 화면 모두에서 확인할 수 있어야 한다.

## 5. 두 자원의 정의

| 구분 | 게임 예산 | EP |
|---|---|---|
| 의미 | 오늘의 프롬프트 과제에 사용하는 게임 내 자원 | 꾸미기용 누적 포인트 |
| 획득 | 액션 게임 기록 | 코인 수집, 챌린지 성공, 출석·팁·개선기 체험 |
| 사용 | 키워드 카드·모델 선택 | 정원 아이템·캐릭터·맵 테마 |
| 실제 에너지인가 | 아니오 | 아니오 |
| 현금·토스 포인트인가 | 아니오 | 아니오 |

게임 예산과 EP는 이름·아이콘·색상을 구분한다. 게임 예산을 실제 토큰 수·Wh 또는 API 결제 잔액으로 표시하지 않는다. 게임 예산의 최종 단위명은 미정이다.

## 6. 액션 게임 규칙

### 확정

- 하루에 제공되는 게임은 한 종류다.
- 액션 게임 플레이는 하루 최대 **5회**다.
- 멀리 이동한 거리·진행 기록 등을 게임 예산으로 환산한다.
- 중간에 획득한 코인은 EP 보상으로 처리한다.
- 게임을 잘해 더 많은 예산을 확보한 사람의 이점을 보정하거나 제거하지 않는다.
- 게임 플레이 횟수와 프롬프트 챌린지 제출 횟수는 독립된 제한이다.
- 원작 게임의 캐릭터·로고·화면·음원·맵 에셋을 그대로 사용하지 않는다.

### 게임 유형

| 유형 | 참고하는 방식 | 기록 | 코인 |
|---|---|---|---|
| 길 건너기형 | Crossy Road의 전진·장애물 회피 | 전진 칸 수·거리 | 경로상의 수집물 |
| 전진 러너형 | Temple Run의 회피·차선 선택 | 생존 거리 | 경로상의 수집물 |
| 장애물 러너형 | Super Penguins의 달리기·점프 | 생존 거리 | 경로상의 수집물 |

**제안:** 첫 개발은 한 종류로 핵심 흐름을 완성하고 이후 게임을 추가한다. 비교할 게임은 하루 하나이므로 서로 다른 게임 간 기록을 정규화한 순위 기능은 만들지 않는다.

### 미정

- 5회 중 최고 기록을 예산으로 사용할지, 다른 집계 방식을 사용할지.
- 기록→예산 환산식, 최소·최대 예산, 예산의 이월 여부.
- 플레이 도중 앱 종료 시 횟수 소모·복구 기준.
- 코인→EP 환산율과 일일 획득 상한.
- 챌린지 성공 후 남은 게임을 계속할 수 있는지와 예산 처리 방식.

## 7. 이미지 프롬프트 챌린지 규칙

### 확정

- 1차 목표와 결과 콘텐츠는 **이미지만** 제공한다.
- 플레이어는 예산 안에서 필요한 키워드 카드와 모델을 고른다.
- 카드는 원하는 것만 선택하고 순서를 바꿀 수 있다.
- **게임 챌린지에는 직접 문장 수정·자유 텍스트 추가 기능을 제공하지 않는다.**
- 앱이 선택된 카드를 자연스러운 프롬프트 문장으로 조합해 보여준다.
- 모델은 고성능·저성능의 두 등급을 기본으로 한다.
- 제출은 하루 최대 **5회**다.
- 일반 실패 시 해당 제출에 사용한 예산은 복구되고 제출 횟수는 소모된다.
- 시스템 오류·대응 결과물 누락은 일반 실패와 구분한다. 횟수·예산을 소모시키지 않는다.
- 플레이어마다 새 이미지를 생성하지 않고 사전 생성·검수된 결과물을 제공한다.

조합 예시:

`사과 / 두 개 / 빨간색 / 흰 배경 / 위에서 보기 / 수채화`

→ “흰 배경 위에 빨간 사과 두 개를 배치하고, 위에서 내려다보는 구도의 수채화로 표현해줘.”

배우는 내용은 조건 선택·조합, 대상 간 관계, 모델 선택이다. 자유로운 문장 작성 능력을 직접 평가하는 서비스로 설명하지 않는다.

### 키워드 데이터

`ID / 표시 문구 / 범주 / 비용 / 의미 속성 / 대상과의 연결 / 충돌 규칙 / 조합 순서`

관계가 있는 과제는 단순 나열 대신 “고양이 왼쪽의 강아지”처럼 속성·관계가 어느 대상에 연결되는지 표현해야 한다. 같은 의미를 중복 선택해도 점수가 중복 증가하지 않는다.

## 8. 판정과 모델별 임계값

### 확정된 판정 방향

**같은 키워드 조합이라도 고성능 모델은 의도를 더 잘 해석한다는 가정에 따라 통과 임계값을 다르게 적용한다.**

| 항목 | 저성능 모델 | 고성능 모델 |
|---|---|---|
| 선택 비용 | 상대적으로 낮음 | 상대적으로 높음 |
| 통과 임계값 | 더 높음 | 더 낮음 |
| 전략 | 조건을 더 정확히 지정 | 모델에 자원을 더 쓰고 일부 조건의 생략을 허용 |

예시: 저성능 85점, 고성능 70점. **수치는 확정값이 아니며 과제 검수 후 설정한다.** 모델별로 배점을 별도로 바꾸는 것은 현재 확정 사항이 아니다. 기본안은 같은 조건 점수에 서로 다른 통과 임계값을 적용하는 것이다.

이 차이는 **모델 성능 차이를 표현하는 게임 규칙**이다. 실제 특정 모델의 이해 능력을 측정한 값이나 실험적으로 검증된 성공 확률로 표시하지 않는다.

### 조건 점수 예시

목표: 흰 배경 위의 빨간 사과 두 개를 위에서 본 수채화.

| 조건 | 예시 배점 |
|---|---:|
| 대상: 사과 | 25 |
| 개수: 두 개 | 20 |
| 색상: 빨간색 | 15 |
| 배경: 흰색 | 15 |
| 구도: 위에서 보기 | 15 |
| 스타일: 수채화 | 10 |
| 합계 | 100 |

배점은 서비스용 제안이며 논문의 검증된 배점표가 아니다. 과제마다 평가 항목·가중치·모델별 임계값을 저장한다.

**제안된 안전장치:** 필수 대상 오류나 명백한 모순은 고성능 모델도 통과시키지 않는다. 필수 조건·충돌 시 감점 방식은 과제별로 정하고 사용자에게 설명한다.

판정 예시:

`통과 = 필수 조건 충족 AND 차단되는 충돌 없음 AND 조건 점수 >= 선택 모델의 임계값`

### 결과 검색과 성공 판정의 분리

1. 선택된 카드 ID에서 조건·관계·충돌을 계산한다.
2. 선택 조건과 모델 등급에 맞는 검수된 대표 결과물을 조회한다.
3. 대응 결과물의 적합성을 확인한 뒤 저장된 규칙으로 성공 여부를 계산한다.
4. 점수·임계값·조건별 충족 여부·관련 팁을 반환한다.

유사도나 군집화는 대표 결과물을 찾는 보조 수단이다. 임베딩 유사도 0.8을 “목표 달성도 80%”로 바꾸어 표시하지 않는다. 사용자에게 보여주는 숫자는 정의된 조건별 목표 달성 점수다.

모든 카드 조합의 이미지를 생성하는 대신 의미가 유사한 조합을 대표 조건군으로 묶는다. 다만 필수 대상·개수·중요 관계가 다른 선택을 같은 결과로 무리하게 매칭하지 않는다. 지원하지 못하는 조합은 대응 오류로 처리하고 횟수를 복구한다.

고성능의 낮은 임계값으로 통과하는 조합도 성공에 맞는 결과 이미지를 준비해야 한다. 점수상 성공인데 결과물이 명백히 목표와 다른 콘텐츠는 공개하지 않는다.

### 피드백

가장 중요한 미충족 조건에 맞는 팁 한 개를 제공한다. 예: “대상은 맞지만 개수 조건을 빠뜨렸어요.” 더 적은 자원으로 성공한 조합을 권할 때는 실제 검수된 조합이 있어야 한다. 무조건 짧게 쓰거나 저성능 모델을 고르라고 안내하지 않는다.

## 9. EP 경제와 성공 보상

### 확정

- 코인 EP는 수집 보상이다.
- 성공 EP는 목표 달성과 남은 게임 예산에 대한 보상이다.
- 성공 시 **남은 예산의 절대량**이 많을수록 EP가 늘어난다. 남은 비율로 보정하지 않는다.
- 출석, 팁 확인, 프롬프트 개선기 사용 체험에도 일일 보상을 제공한다.
- EP 소비처는 정원 꾸미기·게임 캐릭터·맵 테마다.
- 구매한 캐릭터·맵은 능력치·점수·예산·판정에 유리함을 주지 않는 외형 요소로 설계한다.

### 제안 공식

`성공 EP = 기본 보상 + floor((제출 직전 예산 - 선택 비용) × 보상 계수)`

기본 20 EP, 계수 0.1을 가정한 예:

| 제출 직전 예산 | 선택 비용 | 남은 예산 | 성공 EP |
|---|---:|---:|---:|
| 100 | 30 | 70 | 27 |
| 100 | 60 | 40 | 24 |
| 150 | 30 | 120 | 32 |

위 기본값·계수는 예시다. 일반 실패에는 성공 EP를 지급하지 않는다.

**제안:** 성공 보상은 하루 첫 성공 시 한 번 확정하고, 이후 기록 향상에 따른 소급 추가 지급은 하지 않는다. 출석·팁·개선기 보상도 항목별 하루 한 번으로 제한한다. 최종 보상표·지급 조건·상한은 미정이다.

서버에서 EP 거래 원장을 관리한다. 같은 요청의 재전송·새로고침·결과 재열람으로 EP가 다시 지급되지 않아야 한다. 개선기 사용 보상은 원문·개선 결과를 공개하도록 요구하지 않는다.

## 10. 프롬프트 개선기와 모델 추천 시뮬레이션

### 기능

사용자가 직접 원문을 입력하고 개선 버튼을 누르면 의도 보존을 우선으로 명확한 목적·맥락·범위·출력 형식을 정리한다. 개선안, 수정 이유, 학습 팁, 적합한 모델 등급, 비용·사용량 시뮬레이션을 함께 보여준다.

- 원문과 수정안을 비교하고 수정안을 편집·복사할 수 있다.
- 개선안을 외부 AI에 자동 제출하지 않는다.
- 정보가 부족하면 모르는 요구를 사실처럼 추가하지 않고 추가 질문·선택 항목으로 제안한다.
- 오류 시 원문을 보존하고 사용자가 다시 시도할 수 있게 한다.
- 게임의 자유 입력 금지와 별개로, 개선기는 자유 입력 기능이다.

### 참고와 구현 구분

- **Kiro Prompt Optimizer:** 모호한 요청을 구조화된 지시로 정리하는 UX 참고. Kiro의 기능을 호출하는 공개 API가 있다는 전제로 구현하지 않는다.
- **RouteLLM:** 강한 모델·약한 모델 사이에서 품질과 비용을 고려해 라우팅하는 접근 참고. 프롬프트 재작성 도구 자체는 아니다.
- 초기에는 Gemini 한 번의 호출에서 개선·설명·과제 분류·모델 추천을 함께 받는 방식을 제안한다.
- 실제 RouteLLM 프레임워크를 배포·검증하지 않으면 “RouteLLM 원리를 참고한 모델 선택 시뮬레이션”으로 표시한다.
- 비교를 위해 실제 두 모델을 모두 실행할 필요는 없다. 그 경우 응답 품질을 실측 비교했다고 표현하지 않는다.

### 사용량·비용 표시

입력 토큰 계산 방법, 출력 길이 가정, 사용한 가격표와 기준일을 함께 저장한다. 개선문이 길어졌는데도 사용량이 줄었다고 단정하지 않는다. 개선기 자체의 API 호출 비용도 발생한다.

추정 비용, 게임 예산, 물리적인 전력량은 서로 다른 값이다. 토큰이나 가격만으로 실제 전력 사용량·탄소 절감량을 확정해 표시하지 않는다.

### 호출 제한

사용자별 일일 제한, 입력·출력 길이 제한, 전체 서비스 지출 상한을 서버에서 적용한다. 일일 제한 숫자는 미정이다. 중복 요청 방지와 처리 중 버튼 잠금을 제공하고, 실패한 호출의 이용 횟수 복구 정책을 정한다.

Google 무료 크레딧은 종류마다 적용 범위가 다르므로 실제 Gemini API에 적용 가능한지 확인한다. 일반 GCP 가입 크레딧을 AI Studio API에서 당연히 사용할 수 있다고 예산을 잡지 않는다.

## 11. 정원과 소셜

### 정원

쥬니어네이버 동물농장처럼 수집한 소품을 배치하고 나만의 공간을 보여주는 경험을 지향한다. 식물·화분·울타리·배경·장식을 EP로 구매해 보관함에 저장하고 배치한다. 게임 캐릭터도 정원에서 표시할 수 있다.

**제안:** 1차는 배치·저장·방문에 집중하며 물주기·성장 타이머·방치 페널티는 제외한다. 정원 편집은 미리보기 후 저장하고 마지막으로 저장된 배치를 방문자에게 보여준다.

### 친구와 공유

- 토스 로그인에 연결된 내부 사용자 ID로 친구 관계를 관리한다.
- 친구 코드 또는 초대 링크로 연결하고 수락 후 친구 목록에 표시하는 방식을 제안한다.
- 친구 정원과 공개 설정된 챌린지 달성 상태를 볼 수 있다.
- 고정된 이모지 반응은 선택 기능으로 둔다.
- 토스 친구 목록을 자동으로 가져올 수 있다는 전제로 설계하지 않는다.
- 게시판·대화·랭킹·실시간 동시 접속 정원은 만들지 않는다.
- 프롬프트 개선 원문·개선 결과를 기본 공개하지 않는다.

친구 삭제·차단·공개 범위와 초대 만료 규칙은 구현 전에 정한다. 공유 링크는 미니앱 내부의 해당 정원으로 연결되는 방식으로 설계한다.

## 12. 일일 콘텐츠 업데이트와 유지보수

### 코드 배포 없이 교체하는 구조

게임 엔진과 일일 콘텐츠를 분리한다. DB에 날짜별 미션을 미리 등록하고 서버가 한국 시간의 오늘 날짜에 맞는 공개 버전을 반환한다.

`한국 시간 날짜 확인 → 해당 날짜의 공개 콘텐츠 조회 → 게임·목표·평가표 반환`

예:

| 날짜 | 게임 | 목표 |
|---|---|---|
| 2026-11-09 | 길 건너기 | 빨간 사과 이미지 |
| 2026-11-10 | 러너 | 고양이 이미지 |
| 2026-11-11 | 길 건너기 | 풍경 이미지 |

- 요일별 게임 교체·목표 이미지·카드·배점 등록에는 별도 일일 배포나 GitHub Actions가 필요하지 않다.
- 앱을 계속 켜둔 경우 날짜가 바뀌면 콘텐츠를 다시 조회한다.
- 실제 새 게임 로직·화면·기능을 추가할 때는 코드 배포와 앱인토스의 해당 배포 절차가 필요하다.
- 제출에는 날짜와 콘텐츠 버전을 포함한다. 자정에 진행 중이던 도전의 인정 기준은 미정이며 서버에서 일관되게 처리한다.

### 콘텐츠 제작·발행 흐름

1. 목표 이미지와 요구 조건을 정한다.
2. 카드·비용·모델 옵션·평가표를 작성한다.
3. 가능한 주요 조합을 의미별 대표 조건군으로 묶는다.
4. 대표 결과 이미지를 사전 생성한다.
5. 조건 충족·점수·모델 임계값과 결과 이미지의 일치 여부를 검수한다.
6. 정상 조합·실패 조합·충돌 조합·모델별 경계 조합을 테스트한다.
7. 버전을 고정하고 공개 날짜를 예약한다.

**제안:** 2~4주 분량을 미리 준비하고 주 단위로 다음 콘텐츠를 검수한다. 자동 생성 즉시 공개하는 방식은 사용하지 않는다. 신규 콘텐츠가 없을 때 재사용할 검수된 대체 미션을 둔다.

첫 운영 도구는 JSON·CSV 일괄 등록 스크립트로 충분하다. 일정이 안정되면 달력형 관리자 화면을 추가한다. 자동 이미지 생성·일괄 처리까지 원할 때만 별도의 예약 실행 도구를 추가한다.

## 13. 기술 스택과 서비스 구성

아래는 개발을 위한 **제안 스택**이다. 실제 패키지 버전과 앱인토스 SDK는 착수 시 공식 문서에 맞춰 고정한다.

| 계층 | 제안 | 역할 |
|---|---|---|
| 미니앱 | React + TypeScript + Vite + 앱인토스 WebView SDK | 화면·로그인 진입·공유·게임 연결 |
| 3D 게임 | Three.js, 필요 시 React Three Fiber | 3D 렌더링·게임 오브젝트 |
| 2D 대안 | Phaser | 2D 게임을 선택할 때 사용. 초기부터 두 엔진을 모두 도입하지 않음 |
| API | Node.js + TypeScript | 인증·판정·보상·콘텐츠·Gemini 호출 |
| API 호스팅 | Render | HTTPS API 서버 |
| DB | Supabase PostgreSQL | 사용자·미션·시도·경제·정원·친구 |
| 파일 | Supabase Storage | 목표·대표 결과 이미지·정적 에셋 |
| LLM | Gemini API | 개선기·설명·모델 추천 |
| 운영 | 콘텐츠 등록 스크립트 | 검수 콘텐츠의 DB·Storage 등록 |

### 초기 불필요한 구성

- 별도 CLIP·GPU 서버, Redis, 작업 큐, 실시간 소셜 서버.
- Google·Apple 로그인 및 로그인용 이메일 인증 흐름.
- Apple Developer Program, HealthKit, Capacitor 네이티브 셸.
- 미니앱 본체를 위한 별도 Vercel 사이트. 별도 홍보·관리 웹이 필요해질 때 검토한다.

토스 로그인 결과와 내부 사용자 ID를 서버에서 연결한다. 서버 간 토스 API 인증·인증서 설정은 공식 연동 방식으로 구현한다. 로그인 방식 때문에 Supabase Auth의 이메일 인증을 필수 도입하지 않는다.

Supabase는 개발 단계에서 무료 플랜으로 시작할 수 있다. DB·이미지·다운로드 트래픽·백업·일시 정지 조건을 보고 유료 전환을 결정한다. Render 비용과 Gemini 사용료는 별도다. 최신 한도·요금은 공식 가격표에서 확인한다.

### 서버가 결정해야 할 것

시도 횟수, 게임 기록의 인정 여부, 예산, 카드 비용, 점수, 임계값, 성공 여부, EP 지급·차감은 서버가 결정한다. 클라이언트가 보낸 점수·잔액을 그대로 저장하지 않는다.

EP 지급과 관련 상태 변경은 트랜잭션으로 처리한다. 작업별 중복 방지 키를 두어 네트워크 재전송에도 한 번만 지급한다. API 키·DB 관리자 키·토스 서버용 인증 정보는 클라이언트에 포함하지 않는다.

게임은 서버가 발급한 플레이 ID와 필요 시 시드·진행 시간·주요 이벤트를 사용해 비현실적인 기록을 거른다. 완전한 치팅 방지 시스템을 1차 목표로 삼지는 않되 임의 숫자 제출만으로 보상을 지급하지 않는다.

## 18. 구현 순서와 검증 기준

### 제안 순서

1. 미정 규칙 확정, 공유 데이터 타입과 콘텐츠 한 세트 작성.
2. 토스 로그인·DB·EP 원장·일일 제한 구현.
3. 게임 한 종류와 기록·코인·예산 처리 구현.
4. 키워드·모델 조합, 모델별 임계값 판정, 사전 결과 조회 구현.
5. 성공 보상·정원 구매·배치 저장 연결.
6. 프롬프트 개선·모델 시뮬레이션과 호출 제한 구현.
7. 친구 초대·정원 방문 구현.
8. 주간 콘텐츠 등록·날짜 전환·기기 테스트·출시 준비.

### 필수 검증

- 게임 최대 5회와 챌린지 최대 5회가 독립적으로 적용된다.
- 같은 조합·모델·콘텐츠 버전은 같은 판정을 반환한다.
- 같은 점수라도 모델별 임계값에 따라 결과가 달라진다.
- 필수 조건·충돌·임계값 경계의 결과가 규칙과 일치한다.
- 실패 시 예산이 복구되며 일반 실패와 시스템 오류의 횟수 처리가 다르다.
- 재전송·새로고침·중복 콜백으로 EP가 중복 지급되지 않는다.
- 성공 보상은 남은 예산의 절대량을 기준으로 계산한다.
- 결과 이미지가 선택 조건·모델·판정과 의미적으로 일치한다.
- 아이템 구매·EP 차감이 함께 성공하거나 함께 취소된다.
- 정원 저장·재접속·친구 방문 시 배치가 유지되고 비공개 데이터가 노출되지 않는다.
- 날짜 변경·콘텐츠 누락·자정 경계·앱 이탈을 일관되게 처리한다.
- 개선기 호출 제한·오류·중복 요청·원문 보존을 확인한다.
- 실제 토스 환경에서 게임 조작·메모리·로딩·공유·복귀를 확인한다.

## 19. 개발 전 남은 결정

1. 서비스명, 게임 예산 단위명.
2. 첫 게임 종류 및 2D·3D 엔진 선택.
3. 게임 기록 집계·예산 환산·이월·최소·최대 규칙.
4. 키워드 가격, 모델 가격, 과제별 배점·모델별 임계값.
5. 필수 조건과 충돌 처리의 최종 규칙.
6. 코인 환산율, 성공 보상 기본값·계수·상한, 일일 성공 보상 정책.
7. 출석·팁·개선기 보상량과 인정 조건.

9. 정원 초기 아이템 수, 가격표, 배치 방식, 친구 공개 범위.
10. 자정 진행 중 플레이·제출의 귀속 기준과 중단 복구 규칙.
11. 콘텐츠 준비량·검수 담당·일괄 등록 도구의 범위.
