## 1. 서비스 범위

### 1.1 핵심 기능

| 기능 | 제공 가치 | 입력 | 결과 |
|---|---|---|---|
| 일일 게임·이미지 프롬프트 챌린지 | 목표 조건·모델·자원 배분 학습 | 게임 기록, 키워드 카드, 모델 등급 | 사전 제작 결과 이미지, 판정, 피드백, EP |
| 프롬프트 개선기 | 실제 개선과 작성 예시·팁을 통한 학습 | 사용자가 입력한 프롬프트 | 개선안, 확장 예시, 연결된 말풍선 팁 |
| AI 모델 추천 | 필요한 성능 아래 예상 비용 최소화 | 직접 입력 또는 개선기에서 선택한 최종 문장 | 추천 모델, 근거, 대안·예상 비용 |
| 정원·소셜 | 보상 사용과 꾸미기·방문 | EP, 보유 아이템, 정원 배치 | 나의 정원과 친구 방문 경험 |

### 1.2 확정된 제한

- 출시 목표는 앱인토스 미니앱이다. 기존 오프라인 이미지 생성·자전거·열전사 영수증 프로젝트와 분리한다.
- 1차 게임의 목표·결과 콘텐츠는 **이미지만** 지원한다.
- Chrome 확장 프로그램·외부 채팅 사용량 수집·토큰 연동은 제외한다.
- 피트니스·운동 기록·HealthKit·OCR·수동 운동 입력은 제외한다.
- 자유 게시판·채팅·랭킹·실시간 멀티플레이·현금성 EP는 제외한다.
- 게임 챌린지에 자유 문장 입력·수정은 없다. 개선기·모델 추천에는 자유 입력이 있다.
- 게임 플레이 중 매번 이미지 생성·LLM 판정·CLIP 실행을 하지 않는다.
- 실제 전력·탄소 배출량 측정 또는 토큰 기반 전력 확정 환산은 이번 기능에 포함하지 않는다.

## 2. 전체 아키텍처

```text
[앱인토스 미니앱]
React / TypeScript / 게임 렌더링
       │ HTTPS, 사용자 세션
       ▼
[Render API 서버]
인증 / 게임 검증 / 조건 판정 / EP 거래 / 개선기 / 추천 엔진
       ├── Supabase PostgreSQL: 상태·규칙·추천 데이터
       ├── Supabase Storage: 이미지·정적 에셋
       ├── Gemini 텍스트 API: 개선·예시·팁·질문 분석
       └── 토스 서버 API: 공식 인증 방식으로 필요한 연동

[콘텐츠 제작 스크립트]
학습 목표 → LLM 카드 초안 → 이미지 생성·편집 → 검수 → 예약 공개
       └── 검수된 콘텐츠를 DB·Storage에 저장

[GitHub Actions: 주간 모델 데이터 갱신]
Artificial Analysis + OpenRouter → 검증 → 새 스냅샷 → 활성 버전 교체
```

게임 사용자 경로, LLM 사용자 경로, 콘텐츠 제작, 외부 데이터 갱신을 분리한다. API 서버 한 대 안에서도 기능 모듈은 분리하되 초기부터 마이크로서비스로 쪼개지 않는다.

## 3. 기술 스택과 서비스 선정

다음은 **제안 스택**이다. React·게임 엔진·프레임워크의 구체적인 버전은 공식 앱인토스 템플릿과 호환성을 확인한 후 고정한다.

| 영역 | 선정안 | 역할·이유 |
|---|---|---|
| 미니앱 | React + TypeScript + Vite + 앱인토스 WebView SDK | 화면·상태·토스 연동 |
| 화면 상태 | TanStack Query, 필요 시 Zustand | 서버 상태와 게임·편집 임시 상태 구분 |
| API 서버 | Node.js + TypeScript + Fastify | 단일 언어 타입 공유, 요청·응답 스키마 검증 |
| 데이터 계약 | Zod 또는 JSON Schema | LLM 응답·HTTP 입력·콘텐츠 검증 |
| 3D 게임안 | Three.js, 필요 시 React Three Fiber | 도로·러너·정원 에셋 재사용 |
| 2D 대안 | Phaser | 픽셀·2D 방식을 선택할 경우 사용. 초기 두 엔진 동시 도입은 피함 |
| DB | Supabase PostgreSQL | 사용자·경제·게임·콘텐츠·추천 데이터 |
| 파일 | Supabase Storage | 목표 이미지·대표 결과·게임 에셋 |
| 호스팅 | Render Web Service | HTTPS API, 서버 비밀정보 관리 |
| 텍스트 LLM | Gemini API | 개선·확장 예시·설명·질문 구조화 |
| 이미지 제작 | Gemini 이미지 생성·편집 API 우선 검토 | 원본을 참조한 조건별 변형 이미지 사전 제작 |
| 시각 거리 도구 | LPIPS 또는 검증된 이미지 임베딩, 선택 도입 | 콘텐츠 제작 시만 계산 |
| 제작 도구 | TypeScript CLI, 필요 시 Python 보조 도구 | 일괄 등록·생성·검수·이미지 전처리 |
| 예약 작업 | GitHub Actions | 모델 데이터 주간 갱신·수동 재실행 |
| 검증 | Vitest, API·DB 통합 검증, 필요 시 Playwright | 경제·판정·외부 데이터 매칭 등 핵심 검증 |

### 3.1 인프라를 늘리지 않는 기준

- 상시 CLIP·GPU 서버는 필요하지 않다.
- 이미지 거리 계산을 도입해도 사전 제작 PC·배치 환경에서만 실행하고 결과 수치를 저장한다.
- Redis·Celery·별도 메시지 큐·실시간 소셜 서버는 초기 필수 사항이 아니다.
- 사용자 개선 요청이 실제 타임아웃을 일으키거나 재시작 복구가 필요해질 때 DB 기반 작업 처리·폴링을 추가한다. 재시작에 취약한 프로세스 메모리만 작업 원장으로 쓰지 않는다.
- 미니앱 본체는 앱인토스 배포 경로를 따른다. 별도 Vercel 배포를 필수로 넣지 않는다.
- Supabase는 무료로 개발 시작 가능하다. 정식 운영 시 저장량·트래픽·백업·일시 정지 조건을 보고 유료 전환을 결정한다.
- Google API 크레딧 종류에 따라 적용 범위가 다르다. 일반 Cloud 가입 크레딧이 AI Studio API에 적용된다고 가정하지 않는다.

## 5. LLM 활용 범위

| 처리 | 생성·분석 모델 | 호출 시점 | 플레이 중 필요 여부 |
|---|---|---|---|
| 원문 개선 | 텍스트 LLM | 사용자 요청 | 개선기에서만 |
| 확장 예시·말풍선 | 텍스트 LLM | 개선 호출에 포함 | 개선기에서만 |
| 직접 입력 질문 분류 | 텍스트 LLM | 추천 요청 | 직접 입력 경로에서 필요 |
| 개선문 질문 분류 | 텍스트 LLM | 개선 호출에서 함께 생성 | 동일 문장이면 재사용 |
| 목표 조건·카드 후보 | 텍스트 LLM | 제작 배치 | 불필요 |
| 목표·변형 이미지 | 이미지 생성·편집 모델 | 제작 배치 | 불필요 |
| 생성 이미지 조건 검수 | 비전 지원 모델 | 제작 배치 | 불필요 |
| 카드 점수·통과 판정 | 코드·DB | 제출 시 | LLM 불필요 |
| 모델 순위·예상 비용 | 코드·DB | 추천 시 | 추가 생성 호출 불필요 |
| EP·횟수·친구·정원 | 코드·DB | 기능 요청 시 | LLM 불필요 |

모델 추천용 새 입력에는 분석 호출이 발생할 수 있다. 개선문을 편집했다면 최종 문장 해시가 달라지므로 기존 분석을 무조건 재사용하지 않는다. 서버가 보관한 분석과 문장 해시·분석 버전을 확인한다.

## 6. 일일 게임과 두 자원

### 6.1 확정 규칙

- 하루 게임은 한 종류. 길 건너기·Temple Run형 러너·Super Penguins형 러너로 확장 가능하다.
- 액션 게임 최대 **5회/일**, 프롬프트 챌린지 제출 최대 **5회/일**. 서로 다른 카운터다.
- 게임 기록으로 게임 예산을 확보하고 코인은 EP로 지급한다.
- 예산은 카드·모델 선택용 게임 자원이다. 실제 API 토큰·전력·현금과 다르다.
- EP는 꾸미기용 누적 포인트다. 정원·캐릭터·맵 외형 구매에 사용한다.
- 게임 실력이 좋아 확보한 예산이 큰 사람의 이점은 보정하지 않는다.
- 일반 실패는 제출 횟수 소모·예산 복구. 시스템 오류·대응 이미지 오류는 횟수·예산 복구.
- 구매 외형으로 게임 기록·점수·판정에 유리한 능력치를 주지 않는 것을 권장한다.

### 6.2 성공 보상

확정 방향은 남은 **절대 예산량**에 비례한 추가 EP다.

```text
성공 EP = 기본 EP + floor((제출 직전 예산 - 선택 비용) × 계수)
```

예시: 기본 20, 계수 0.1. 예산 100·비용 30이면 27 EP, 예산 150·비용 30이면 32 EP. 이 숫자와 상한은 미정이다.

출석·팁 확인·개선기 체험에도 보상한다. **제안:** 항목별 하루 한 번, 성공 보상도 첫 성공 한 번 확정·소급 증액 없음. 코인 환산·예산 집계·이월·중단·성공 후 플레이 정책은 아직 미정이다.

## 7. 공통 프롬프트 조건 모델

게임·카드·이미지 제작·피드백에서 공통 의미 체계를 사용한다.

| 요소 | 예시 |
|---|---|
| 대상 | 사과, 고양이 |
| 속성 | 빨강, 두 개, 금속 |
| 행동·관계 | 앉아 있음, 접시 위, 고양이 왼쪽 |
| 배경 | 흰색, 숲 |
| 표현 | 수채화, 위에서 보기, 부드러운 조명 |
| 제약 | 글자 없음 |

대상 ID와 속성·관계의 연결을 보존한다. 두 대상의 색상과 위치를 바꾸어도 같은 단어 목록이 될 수 있으므로 문자열·집합만 비교하지 않는다.

```json
{
  "entities": [{"id": "apple_a", "type": "apple", "count": 2}],
  "attributes": [{"entity": "apple_a", "key": "color", "value": "red"}],
  "scene": {"background": "white", "view": "top_down", "style": "watercolor"}
}
```

## 8. LLM 기반 키워드 후보 생성

### 8.1 근거와 적용 범위

T2I-CompBench의 사전 규칙·LLM을 이용한 조합형 프롬프트 구성, 속성 연결·관계 분류를 참고한다. 교육용 오답·비용·커리큘럼은 우리 서비스 설계이며 논문이 학습 효과를 보장하는 것은 아니다.

### 8.2 제작 절차

1. 학습 항목 1~2개 선택: 개수, 색상 연결, 구도, 관계 등.
2. 목표 장면과 평가 가능한 조건 구조 작성.
3. 목표 이미지 생성 또는 운영자 원본 등록. 원본의 실제 속성과 목표 정의 일치 확인.
4. LLM이 카드 후보·학습 이유·의미 속성·충돌·변형 이미지 지시를 JSON으로 생성.
5. 코드로 범주·참조 무결성·중복·충돌·비용을 검증.
6. 가능한 조합·성공 경계·이미지 매칭 커버리지 검사.
7. 운영자 확인 후 콘텐츠 버전 발행.

### 8.3 후보 유형

| 유형 | 예 | 학습 역할 |
|---|---|---|
| 일치 조건 | 두 개, 위에서 보기 | 목표 관찰·필수 정보 선택 |
| 근접 오답 | 한 개, 옆에서 보기 | 세부 조건 구분 |
| 다른 과제에서는 유용 | 금속 질감, 도시 배경 | 관련성 판단 |
| 모호한 표현 | 멋지게, 최고 품질 | 구체적인 지시와 비교 |

단순 무의미 단어만 오답으로 만들지 않는다. 필수 조건이 이미지에서 분명히 관찰 가능해야 하며 애매한 개수·가려진 대상은 피한다. 표현만 다른 동의어 카드를 별도 정답 점수로 누적하지 않는다.

```json
{
  "id": "count_two",
  "label": "두 개",
  "category": "count",
  "target_entity": "apple_a",
  "value": 2,
  "cost": 8,
  "learning_tag": "specify_count",
  "conflicts_with": ["count_one"]
}
```

비용 8은 예시다. 후보 생성 LLM의 제안 비용·점수는 최종 규칙이 아니다. 가격표와 허용 범위를 별도 정책으로 검증한다. LLM에 성능 임계값·EP 지급을 결정시키지 않는다.

### 8.4 후보 표시와 조합

- 초급은 범주와 안내를 표시하고 중급부터 가까운 오답·관계를 늘린다.
- 같은 날의 목표·후보·판정은 사용자별로 임의 변경하지 않는 것을 권장한다.
- 정답 위치 반복을 피하고 카드 가격 자체가 정답 힌트가 되지 않는지 검사한다.
- 카드를 원하는 것만 선택·해제·순서 변경한다. 문장은 템플릿으로 자연스럽게 조합한다.
- 관계 표현이 필요한 경우 대상·관계 구조를 UI에서 직접 지정한다. 문장 순서만 바꿔 뜻이 달라지지 않는 카드에는 임의 순서 가산점을 주지 않는다.
- 배운 항목을 이후 과제에서 다시 확인한다. 성공률만으로 실제 학습 효과를 입증했다고 표현하지 않는다.

## 9. 조건부 판정과 모델별 임계값

### 9.1 텍스트 임베딩보다 조건 매칭 우선

자유 입력이 없는 게임은 카드의 의미를 알고 있으므로 카드 ID에서 구조화 조건을 계산한다. 대상·개수·색상·관계를 전체 문장 유사도로 다시 추측할 필요가 없다.

GenEval·TIFA의 세부 조건 평가를 참고한다. 논문의 평가 시스템 전체를 서버에 도입하는 것이 아니라 조건별 판정·질문 기반 검수 원리를 적용한다.

### 9.2 세 상태를 구별

| 상태 | 예 | 처리 |
|---|---|---|
| 일치 | 두 개 선택 | 해당 조건 점수 |
| 누락 | 개수 미선택 | 미충족·보완 가능 여부 정책 적용 |
| 명시적 오류 | 한 개 선택 | 오류·충돌 정책 적용 |

누락과 오지정을 같게 취급하지 않는다. 고성능이 일부 생략을 보완한다는 게임 가정과, 명시한 틀린 조건을 무시하는 것은 구별한다.

```text
조건 점수 = 충족 배점 합계 - 과제별 충돌 감점
통과 = 필수 조건 충족 AND 차단 충돌 없음 AND 점수 >= 모델별 임계값
```

고성능은 높은 선택 비용·낮은 임계값, 저성능은 낮은 비용·높은 임계값을 적용한다. 예시 임계값 고성능 70·저성능 85는 미확정이다. 필수 의미·차단 오류·보완 가능한 세부 조건은 과제별 검수한다.

이 점수는 **조건 충족 점수**이며 이미지 유사도 퍼센트·실제 모델 성공 확률·실측 이해 능력이 아니다. 실제 모델 벤치마크 기반 추천 엔진의 임계값과도 별개다.

### 9.3 이미지 선택과 판정의 일관성

사용자 지정 조건, 선택 모델의 게임 정책, 대응 이미지의 실제 속성을 함께 확인한다. 입력에서 빠진 조건이 우연히 이미지에 나타났다고 그 조건을 작성한 점수를 추가하지 않는다.

성공 임계값을 넘겼어도 준비된 결과 이미지가 그 상태와 모순되면 운영 콘텐츠 오류다. 이미지가 예뻐 보인다는 이유로 입력 점수를 올리거나, 제작 오류를 사용자 실패로 처리하지 않는다.

## 10. 원본 기반 유사 이미지 사전 제작

### 10.1 제작 목적

목표 원본과 완전히 같은 복사본을 반환하는 대신, 조건을 충족하면서 세부 모양이 다른 성공 이미지와 조건별로 틀린 실패 이미지를 준비한다. 매번 새로운 생성 작업을 실행하지 않고 이 결과군을 조회한다.

| 결과군 | 변경 지침 |
|---|---|
| 성공 변형 | 필수·목표 조건 유지, 세부 간격·질감·윤곽 등 변경 |
| 단일 조건 오류 | 개수·색·배경 등 지정 항목 하나 변경 |
| 복합 오류 | 검수된 여러 조건 변경 |
| 핵심 의미 오류 | 대상·중요 관계 변경 |

### 10.2 우선 생성 방식

원본 이미지와 유지할 조건·바꿀 조건을 Gemini 이미지 편집 API에 전달한다. 대상·색상·개수·구도 보존을 구체적으로 지시한다. 여러 변형은 가능하면 승인된 원본에서 각각 분기하여 연속 편집에 따른 누적 변화를 줄인다.

```text
유지: 빨간 사과 두 개, 흰 배경, 위에서 본 구도, 수채화
변경: 두 사과의 간격과 붓질
목적: 동일 조건을 충족하는 새로운 이미지
```

대안인 Diffusers img2img는 strength로 초기 이미지에 가하는 변화 수준을 조절한다. strength를 최종 이미지의 유사도·거리와 동일시하지 않는다. 직접 모델·GPU 운영 부담 때문에 초기 필수 구성으로 두지 않는다.

모델의 고성능·저성능 게임 등급별 결과를 하나의 제작 모델로 시뮬레이션할 수는 있으나, 이를 실제 두 모델의 생성 성능 비교로 표시해서는 안 된다. 실제 모델 비교를 주장하려면 해당 모델로 생성·검증해야 한다.

### 10.3 거리의 분리

| 지표 | 의미 | 용도 |
|---|---|---|
| 조건 거리 | 목표 속성·관계와의 차이 | 목표 오류 유형·조건 충족 검수 |
| 시각 거리 | 원본과 지각적 외형의 차이 | 지나친 복제·과도한 이탈 제외 |
| 중복 판별 | 동일 파일·거의 동일한 이미지 | 후보군 다양성 관리 |

LPIPS·이미지 임베딩은 선택적 사전 제작 도구다. LPIPS가 낮다고 개수·관계가 맞는 것은 아니다. 해상도·전처리·모델 버전을 함께 기록하고 동일 기준으로 비교한다.

```text
성공 변형 후보 채택 =
목표 조건 검수 통과
AND 원치 않는 변경 없음
AND duplicate 아님
AND 보정된 허용 시각 거리 구간에 포함
```

거리가 0보다 크다는 조건만으로는 충분하지 않다. 작은 노이즈도 거리를 만들기 때문이다. 사람이 분류한 '거의 복제 / 적절한 변형 / 과도한 이탈' 표본으로 과제군별 경계를 정한다. 수치 구간은 현재 미정이다.

### 10.4 자동 검수와 재시도

1. 이미지 손상·크기·파일 형식 검사.
2. 대상·개수·색상·배경·구도 등을 비전 모델에 개별 질문.
3. 변경하지 말아야 할 속성의 유지 확인.
4. 중복·시각 거리 검사.
5. 불일치·불확실 후보만 재생성 또는 운영자 확인.
6. 승인된 결과의 실제 조건·버전·검수 결과를 저장.

자동 검수 모델도 틀릴 수 있다. 초기에는 공개 후보를 사람이 최종 검수한다. 후보별 최대 생성 횟수·일일 제작 비용 상한을 두고 무한 재생성을 막는다.

## 11. 대표 이미지 매칭과 조합 폭발 관리

### 11.1 매칭 순서

```text
과제·버전·모델 등급 제한
→ 명시된 대상·개수·관계와 양립하는 후보 제한
→ 사전 정의된 누락 처리·프로필 적용
→ 남은 속성 차이가 작은 승인 후보 선택
→ 적합 후보 없음: 대응 콘텐츠 오류, 횟수·예산 복구
```

명시적으로 두 개를 골랐는데 한 개 이미지를 반환하지 않는다. 후보가 없을 때 항상 가장 비슷한 이미지를 반환하는 방식은 사용하지 않는다.

### 11.2 축약 원칙

입력 카드 조합 전체와 이미지 파일을 일대일로 만들지 않는다. 의미가 같은 동의어·비의미적 순서는 같은 프로필로 정규화할 수 있다. 반면 개수·대상·관계처럼 중요한 의미 차이는 축약하지 않는다.

초기 후보 수는 과제당 카드 10~15개, 이미지 8~12장부터 실험하는 안이다. 이 숫자가 모든 조합을 커버한다는 뜻은 아니다. 제작 도구가 허용 조합을 열거해 커버리지를 검사하고 부족하면 이미지 추가·후보 축소·명시적 선택 규칙으로 해결한다. 정상적인 사용자 선택이 빈번히 콘텐츠 오류가 되는 상태로 출시하지 않는다.

벡터 검색은 의미 후보가 많아질 때 추가한다. 단순 속성 조회만으로 충분하면 pgvector·임베딩 API를 도입하지 않는다.

## 12. 프롬프트 개선기 상세

### 12.1 두 가지 결과와 설명

| 결과 | 역할 | 추가 정보 처리 |
|---|---|---|
| 개선안 | 기존 의도·제약을 보존하며 실제 문장 개선 | 원문에 없는 사실·목적을 임의 확정하지 않음 |
| 확장 예시 | 대상·분량·형식 등을 지정하는 작성법 시연 | 추가 조건임을 표시 |
| 말풍선·메모 | 바뀐 구절의 이유·활용 팁 | 해당 구절과 연결 |

예시 원문 '재활용 방법 좀 쉽고 간단하게 설명해줘'의 개선안은 '재활용 방법을 쉬운 표현으로 간단하게 설명해줘', 확장 예시는 '초등학생이 실천할 수 있는 재활용 방법 세 가지를 쉬운 말로 설명해줘'처럼 구분한다.

### 12.2 처리 흐름

```text
입력·길이·쿼터 검사
→ LLM: 의도·제약 추출, 진단, 개선, 예시, 팁, 문장별 작업 분석
→ JSON 스키마·의미 제약 검증
→ 개선·예시·말풍선 표시
→ 사용자가 선택·편집한 문장을 모델 추천에 전달
```

이미 명확한 질문은 큰 수정이 없을 수 있다. 사용자에게 불필요한 역할·예시·긴 형식을 자동 삽입하지 않고, 필요한 작성법을 예시와 설명으로 제시한다.

### 12.3 반환 구조 제안

```text
original_text
preserved_constraints[]
rewrite: text, changes[], task_profile
example: text, added_conditions[], task_profile
annotations[]: target_variant, segment_id 또는 연결 구절, tip, learning_tag
clarifications[]
analysis_version
```

텍스트 위치를 LLM의 숫자 오프셋만으로 신뢰하지 않는다. 구절·세그먼트 ID를 확인하고 편집 후 연결이 무효가 되면 팁을 다시 연결하거나 일반 메모로 표시한다.

### 12.4 품질·비용 정책

- 단일 호출로 개선·예시·팁·분석을 함께 얻는 방식을 우선한다.
- JSON 검증이 성공해도 내용 정확성은 보장되지 않는다. 고정 한국어 예제로 의도 보존·제약 누락·임의 추가를 검증한다.
- 원문을 분석 대상 데이터로 취급한다. 원문 내부의 지시로 시스템 분석 규칙을 변경하거나 도구를 실행하지 않는다.
- 사용자별 호출 한도·입출력 길이·동시 요청·전체 지출 상한은 서버에서 적용한다. 숫자는 미정이다.
- 오류 시 원문 보존. 통신 재시도에는 같은 작업 ID를 사용한다.
- 개선안이 길어졌다면 입력량 증가를 그대로 보여준다. 개선이 항상 토큰·비용 감소를 의미하지 않는다.

## 13. 여러 LLM의 벤치마크 기반 비용 최적화

### 13.1 확정 방향

고성능·저성능 두 모델만 선택하는 기능에서, 여러 모델 중 필요한 성능을 충족하면서 예상 비용이 가장 낮은 모델을 추천하는 방식으로 발전했다.

```text
개선기 → 개선안·확장 예시 선택 또는 편집 ─┐
                                         ├→ 질문 분석 → 모델 필터 → 비용 최적화
직접 입력 ───────────────────────────────┘
```

명칭은 **AI 모델 추천 / 모델 추천 시뮬레이션**이 적절하다. RouteLLM·OpenRouter Auto는 참고이며 해당 서비스의 내부 알고리즘을 그대로 구현했다고 표현하지 않는다. 추천 모델의 실제 답변 생성은 1차 범위가 아니다.

### 13.2 데이터 역할

| 출처 | 역할 |
|---|---|
| Artificial Analysis API | 제공 범위 내 성능 지수·속도·평가 버전 |
| OpenRouter 모델 API | 모델 목록·지원 기능·입출력 가격·컨텍스트 등 |
| 자체 검증 | 한국어·요약·변환 등 서비스 작업 적합도 보완 |
| 자체 정책 | 작업·난이도별 최소 기준·예산·추천 근거 |

Artificial Analysis 무료 API가 모든 개별 벤치마크를 제공한다고 가정하지 않는다. 필요한 상세 지표가 없으면 상위 플랜 검토 또는 자체 검증으로 보완한다. 출처 표시와 이용·재배포 조건을 준수한다.

### 13.3 모델 대응표

두 출처의 모델을 이름 유사도만으로 자동 연결하지 않는다. 처음에는 대표 6~10개를 수동 승인한다.

대응 키: 내부 모델 ID, AA 모델·제작자 ID, OpenRouter ID, 정확한 버전, 추론 설정, 적용 제공 경로, 검수 상태.

고추론 설정 점수와 저추론 설정 가격을 혼합하지 않는다. 조건이 비교 불가능하거나 불명확하면 해당 근거를 제외하거나 불확실 상태로 표시한다. 결측값을 0으로 채우지 않는다.

### 13.4 질문 분석

작업 유형, 추론 부담, 입력 규모, 필요한 모달리티·도구, 정확도 요구, 출력 길이 가정을 추출한다. 짧은 질문이라고 단순 작업, 긴 질문이라고 고성능 필요로 판정하지 않는다. 추천을 크게 바꾸는 정보만 부족할 때 추가 질문한다.

LLM이 모델명·가격·벤치마크 점수·절감률을 지어내게 하지 않는다. LLM은 특징을 추출하고 서버가 승인된 데이터로 결정한다.

### 13.5 최적화 식

```text
적격 후보 E(x) =
필수 기능 지원
AND 입력·출력 길이 처리 가능
AND 작업별 평가 근거 확보
AND 작업 적합도 Q(m,x) >= 최소 기준 τ(task, difficulty)

추천 m* = argmin[m in E(x)] 예상 비용 C(m,x)
```

Q는 서비스가 정한 작업 적합 지표이지 개별 질문 성공 확률이 아니다. 서로 다른 벤치마크 원점수를 그대로 합산하지 않는다. 동일 평가 버전 안에서 비교 가능한 지표를 사용하고 정책·자체 검증 버전을 기록한다.

작업 관련 지표가 하나면 해당 지표의 기준으로 단순하게 시작한다. 여러 지표를 합성하려면 정규화·가중치·결측 처리 근거를 먼저 정한다. 이 합성 방식과 실제 τ 값은 미정이다.

적격 후보가 없거나 질문 분류가 불확실하면 '성능 기준 충족 확인 불가'로 표시하고 보수적 대안을 제시한다. 최저가 모델을 억지로 추천하지 않는다.

### 13.6 비용 계산

```text
C = 예상 입력 토큰 × 입력 단가
  + 예상 청구 출력 토큰 × 출력 단가
  + 적용되는 요청·이미지·도구 등의 추가 비용
```

- OpenRouter pricing.prompt·pricing.completion은 문서의 **토큰당 USD 단위**로 해석하고 내부 단위를 통일한다. 백만 토큰 단가와 혼동하지 않는다.
- 정확한 토크나이저를 사용할 수 없으면 추정 입력량이라고 표시한다.
- 출력량·추론 토큰은 아직 생성하지 않았으므로 범위·가정을 명시한다. 답변 길이만 같게 두어도 모델별 총 청구 출력량은 달라질 수 있다.
- 반복 입력 캐시를 확인하지 않았다면 캐시 할인 0을 기본으로 둔다. 무료·프로모션 모델은 조건·제한을 별도 검토한다.
- OpenRouter 가격으로 계산했다면 'OpenRouter API 기준'이라고 표시한다. ChatGPT·Claude 구독 비용과 비교하지 않는다.
- 실제 호출하지 않은 모델의 품질·지연 시간을 실측값으로 표시하지 않는다. AA 측정 속도도 평가 조건과 사용자의 실제 지연이 다를 수 있다.
- 개선·추천 분석을 수행한 Gemini 비용은 별도 운영 원장에 남긴다.

### 13.7 화면 결과

주 추천은 비용 최소화 모델, 보조 후보는 더 높은 성능의 대안으로 제공한다. 추천 이유·예상 비용 범위·대안 대비 차이·출처·기준일·근거 부족 여부를 표시한다.

개선 전후 비교는 같은 가정을 사용한다. 개선문이 복잡해져 고성능 모델이 필요해질 수도 있고, 문장이 정리돼도 추천 모델은 같을 수 있다. 항상 절감됐다는 결과를 만들지 않는다.

### 13.8 RouteLLM·Auto와의 관계

RouteLLM은 강한 모델·약한 모델 라우팅 프레임워크이며 자체 임계값 보정이 필요하다. 실제 도입 전에는 후보 모델 쌍·한국어 분포 검증이 필요하다. 일부 기본 라우터의 임베딩 비용·의존성도 별도로 확인한다.

OpenRouter Auto의 시장 기반 라우팅과 우리 벤치마크 기반 추천은 구분한다. 1차는 Auto 호출이나 RouteLLM 배포 없이 자체 추천식을 실행할 수 있다. 따라서 여러 추천 모델의 API 키를 각각 확보할 필요가 없다.

## 14. 주간 API 갱신·DB 버전 관리

### 14.1 채택 방향

외부 모델 데이터는 주 1회 정도 예약 수집하고 필요 시 수동 갱신한다. 사용자 요청 때마다 외부 평가·모델 API를 호출하지 않는다. 가격 급변·모델 종료가 확인되면 수동 반영한다.

**제안 구현:** GitHub Actions의 schedule + workflow_dispatch로 같은 수집 스크립트를 실행한다.

```text
AA + OpenRouter 수집
→ 임시 스냅샷에 저장
→ 형식·가격 단위·모델 매핑·결측·변동 검사
→ 검증 성공 시 DB 트랜잭션으로 활성 스냅샷 교체
→ 이후 추천 요청부터 새 버전 사용
```

하나의 추천 요청은 같은 스냅샷·정책 버전으로 끝까지 계산한다. 부분 갱신 중의 가격과 점수를 섞지 않는다. 실패 시 마지막 정상 스냅샷을 유지하고 오래된 데이터 경고 기준을 둔다.

### 14.2 비밀정보와 실행

AA API 키·필요한 OpenRouter 키·DB 갱신 자격증명은 GitHub Secrets에 둔다. 가능하면 갱신 전용의 제한된 DB 권한 또는 서버 엔드포인트를 사용한다. 관리자 키를 사용해야 한다면 작업에만 주입하고 로그·저장소에 출력하지 않는다.

수집 작업은 동시 실행을 막고 시간 제한·제한된 재시도·수집 원장을 둔다. 로그에는 성공 여부·수집 건수·검증 실패 이유·스냅샷 ID만 남긴다.

GitHub 예약 실행은 정확한 시각을 보장하지 않는다. 공개 저장소 장기 비활동에 따른 비활성화 조건도 확인한다. 주간 갱신에는 허용 가능하나 날짜 정각 미션 교체를 이 작업에 의존시키지 않는다.

대안은 Supabase Cron → Edge Function이다. 두 스케줄러를 동시에 운영할 필요는 없다. Supabase 프로젝트가 일시 정지되면 DB 접근·내부 예약 작업이 정상 동작한다고 가정하지 않는다.

### 14.3 배포와 데이터 갱신 구분

| 변경 | 필요한 작업 |
|---|---|
| 가격·성능 데이터 | DB 스냅샷 갱신 |
| 미리 지원하는 일일 콘텐츠 | DB·Storage 등록 |
| 정책 설정값 변경 | 검증된 정책 버전 등록 |
| 새 추천 로직·기능 | API 서버 배포 |
| 새 게임·화면·클라이언트 처리 | 미니앱 코드 배포와 필요한 검수 |

## 15. 일일 콘텐츠 공개와 운영

DB에 공개 날짜·미션·승인 버전을 저장한다. 서버가 한국 시간 날짜를 계산해 조회하므로 자정마다 별도 배포·GitHub 실행은 필요 없다.

**제안:** 2~4주 분량 제작, 주 단위 검수. JSON·CSV·CLI 등록부터 시작하고 관리자 달력은 이후 추가한다. 검수된 대체 콘텐츠를 준비한다.

콘텐츠 상태: draft → generated → validated → approved → scheduled → published. 오류 콘텐츠는 retired로 전환하고 진행 기록에 사용된 과거 버전은 보존한다.

앱 복귀·날짜 전환 시 오늘 콘텐츠를 재조회한다. 진행 중 세션은 시작 당시 콘텐츠 버전을 보존하며 자정 이후 인정·만료 유예·횟수 귀속 정책은 구현 전에 정한다.

자동 초안 생성과 자동 공개는 다르다. 초기 공개에는 운영자 승인을 유지한다. 이미지 제작 배치는 길고 비용이 드므로 주간 모델 목록 수집과 별도 작업으로 관리한다.

- 원문·확장 예시의 저장 기간은 미정이다. 분석 메타데이터·정책 버전과 원문 보존을 구분한다.

### 17.2 판정 원자성

콘텐츠 매칭과 규칙 검증을 먼저 완료한 뒤 하나의 DB 트랜잭션에서 횟수·예산·결과·성공 EP를 확정한다. 일반 실패는 최종 잔액에 비용이 남지 않는 결과를 보장하면 되며 불필요한 차감·환급 거래를 강제로 늘릴 필요는 없다. 클라이언트의 예상 비용은 서버가 재계산한다.

응답 전 연결이 끊겨도 같은 요청 ID 재조회로 확정 결과를 복구한다. 재전송으로 횟수·보상이 중복되지 않는다.

### 17.3 게임 기록 검증

서버 발급 플레이 ID·게임 버전·시드·시작/종료 시각·필요한 이벤트를 사용한다. 물리적으로 불가능한 거리·코인·시간 조합과 중복 완료 요청을 거른다. 브라우저 게임의 완전한 치팅 방지를 보장하지 않되 임의 숫자 하나로 경제를 변경하지 않는다.

## 18. 정원·친구와 앱인토스 연동

- 토스 로그인으로 내부 계정에 연결하며 Supabase 이메일·Google·Apple 로그인을 필수로 넣지 않는다.
- 토스 서버 API의 인증서·서버 인증 처리는 공식 방식에 맞춰 구현한다. 지원 SDK·정책은 착수 시 확인한다.
- 친구 코드·초대 공유 → 수락 → 정원 방문 흐름을 제안한다. 토스 친구 그래프를 자동 취득한다고 가정하지 않는다.
- 정원은 저장된 배치 스냅샷을 방문자에게 반환한다. 실시간 서버가 필요하지 않다.
- 개선기 원문·개선문은 기본 공개하지 않는다. 공개 달성 상태와 개인 사용 기록을 구분한다.
- 캐릭터·맵은 외형 변경 중심으로 상품화한다. 정원 물주기·성장 타이머는 1차 필수 범위가 아니다.
- AI 생성 콘텐츠 표시·미니앱 공유·게임 분류·계정 연결 해제·개인정보 처리는 최신 앱인토스 요구사항을 확인한다. 문서만으로 최종 검수 통과를 보장하지 않는다.

## 19. 에셋·성능

### 19.1 에셋 후보

| 후보 | 용도 | 조건 |
|---|---|---|
| Kenney City Kit Roads·Car Kit | 길 건너기 도로·차량 | CC0 패키지 확인 |
| Kenney Nature Kit | 나무·배경·정원 | CC0 |
| Kenney Platformer Kit | 발판·캐릭터 후보 | CC0, 실제 애니메이션 확인 |
| KayKit Platformer·Dungeon·Forest | 러너·신전·숲 테마 | 무료 CC0 범위와 유료 추가 구성 구분 |
| Kenney UI Audio | 효과음 | CC0 |
| Kenney Tiny Town | 2D 정원 대안 | CC0, 3D 에셋이 아님 |
| Sprout Lands | 2D 농장 대안 | 무료판 비상업용, 상업 사용 라이선스 별도 확인 |

Quaternius는 모든 에셋이 CC0라는 전제를 쓰지 않는다. 각 취득 파일의 라이선스를 확인한다. 원작 게임의 에셋·명칭·음악·로고 복제는 범위 밖이다. 두잇 레퍼런스는 제외한다.

출처·제작자·라이선스·취득일·수정 여부·크레딧을 assets/manifest.json과 licenses에 남긴다. 초기에는 스타일이 일관된 한 계열과 캐릭터 한 종부터 시작한다.

### 19.2 로딩·렌더링

- 오늘 게임의 에셋만 지연 로드한다. 모든 게임·에셋 팩을 한 번에 로드하지 않는다.
- GLB·텍스처 크기·재질·애니메이션을 필요한 만큼 줄이고 실제 토스 WebView에서 확인한다.
- 반복 장애물은 풀링·필요 시 인스턴싱을 사용한다. 기기별 해상도 배율을 제한한다.
- 앱 백그라운드 전환 시 렌더 루프·오디오·진행 타이머를 관리한다.
- 메모리·프레임·초기 로딩 목표는 기기 검증 후 수치로 확정한다. 특정 기술 도입만으로 가벼운 앱을 보장하지 않는다.

## 20. 검증·운영 기준

### 20.1 판정·경제

- 게임과 챌린지 5회 제한의 분리·동시 요청 상한.
- 모델별 경계값, 필수 조건·누락·오지정·충돌 처리.
- 같은 버전·입력·모델의 결정적 결과.
- 재시도·재접속·중복 콜백 시 EP·횟수·구매 중복 없음.
- 콘텐츠 오류는 사용자 실패가 아니며 상태 복구.
- 남은 절대 예산량에 따른 성공 보상 계산.

### 20.2 콘텐츠·개선기·추천

- 카드 의미·문장 조합·목표 조건·결과 이미지의 일관성.
- 생성 이미지가 지시하지 않은 필수 조건까지 바꾸지 않았는지 검수.
- 거리 지표만으로 개수·관계 오류를 승인하지 않음.
- 개선안 의도 보존, 확장 조건 표시, 말풍선 연결, 편집 후 재분석.
- 벤치마크 버전·가격 단위·추론 설정 불일치·결측 처리.
- 신규 가격 갱신 실패·스냅샷 교체 중 일관성·오래된 데이터 표시.
- 입력·출력 가정이 다른 비교로 절감률을 부풀리지 않음.

### 20.3 초기 실험 제안

목표 이미지 3개, 모델 등급 2개로 조건 판정·대표 결과 커버리지를 먼저 확인한다. 이후 카드·이미지 수를 확장한다. 개선·추천은 한국어 질문 30~50개로 의도 보존·추천 근거를 확인하고 평가용 문장을 규칙 조정에 쓰는 문장과 분리한다. 이 규모는 초기 결함 발견용이며 서비스 품질을 통계적으로 입증하는 기준은 아니다.

### 20.4 관측 항목

API 처리 시간·오류 유형, LLM 호출/토큰/비용, 추천 데이터 기준일, 콘텐츠 미매칭률, 생성 재시도 비용, 중복 차단 건수, EP 이상 거래를 확인한다. 로그에 원문·키·토스 인증 정보를 무분별하게 남기지 않는다.
