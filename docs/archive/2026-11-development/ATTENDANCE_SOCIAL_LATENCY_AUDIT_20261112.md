# 출석·모모 표시 지연 조사

## 출석

`features/home/screens.tsx`는 출석을 누르면 팝업을 즉시 열고 승인 전에는 ‘출석을 확인하고 있어요’를 표시한다. API 성공 후 승인된 EP만 표시한다. `perform(...,"background")`이므로 콘텐츠/상태 재조회가 보상 표시를 막지는 않는다. 완료 후 ‘확인’은 팝업을 닫는 동작이며 별도 보상 API가 없다. 해당 버튼의 loading은 전역 busy에도 연결되어 있어 다른 작업 중에는 같이 로딩 표시될 여지가 있다.

테스트 계정 경로는 인증SELECT 후 공유행 거래(BEGIN→INSERT ON CONFLICT→SELECT FOR UPDATE→UPDATE→COMMIT)를 수행한다. 기존 계정에도 불필요한 INSERT 왕복이 남아 있으며 공유 계정의 동시 쓰기와 경합할 수 있다. 실제 토스 인증 계정은 별도 wallet/원장 거래이며 공유 테스트 행 경합은 없지만 여러 SQL 왕복과 DB 지연은 적용된다. 거래 승인 전에 지급 완료를 보여주는 방식은 사용하지 않는다.

실제 출석 지급은 사용자 보상을 바꾸므로 이 조사에서 추가 실행하지 않았다. 현재 수치로 실제 보상 API의 정확한 소요 시간을 단정할 수 없다.

## 소셜

`features/garden/screens.tsx`의 Social은 people=[]로 처음 렌더링한 뒤 useEffect에서 /v1/social을 호출한다. 화면 진입 전에 친구가 없던 것이 아니라 응답 전 빈 배열을 표시하는 구조다. 의존성이 a.data여서 관련 없는 홈 상태 갱신에도 소셜을 재조회한다. 오류도 catch에서 숨겨 로딩과 빈 목록을 구별하기 어렵다. 친구 정원 화면에서도 Social 마운트 시 목록과 정원 조회가 함께 실행된다.

테스트 계정 소셜 조회는 인증SELECT→본인상태SELECT→친구 일괄SELECT로3번의 DB 조회를 직렬 실행한다. 기존 N+1 조회는 일괄 조회로 이미 바뀌었으나 첫 진입 네트워크 대기는 남아 있다. 본계정도 화면 마운트 후 조회하는 UI 구조는 같다.

현재 Mac→실제 Render API, 서버가 깨어 있는 조건에서3회 순차 측정: state274/303/273ms, social358/409/342ms. 모모1명 반환. 세션 발급1316ms. 아이폰5G 실측·실제 출석 지급 시간·DB 각 쿼리 시간과는 다르다.

## 개선 후보(이 문서는 조사이며 아직 반영하지 않음)

- 소셜은 인증 세션별 캐시와 명시적 로딩/실패 상태를 제공하고 첫 방문 이전에 미리 조회한다. 새 요청 수락/삭제·초기화·계정 전환 때 캐시를 무효화한다. a.data 전체 변경마다 조회하지 않는다.
- 출석 완료 확인 버튼의 loading은 해당 보상 처리 중에만 연결한다. 승인 응답의 balance/claimed 상태를 즉시 적용하고 재조회는 뒤에서 한다.
- 테스트 거래의 기존 행 INSERT를 제거하려면 계정 생성 때만 행을 만들고 실제 쓰기는 기존 행 잠금부터 시작하도록 분리한다. 원장·중복 지급 방지·동시성은 유지한다.
