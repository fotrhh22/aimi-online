# AIMI LLM 4개 기능 상세 설계안

작성: 2026-11-08. 사용자의 4개 기능 구체화 요청에 따른 설계 초안이다. 프롬프트 초안은 작성했으나 기능 코드·운영 정책·이미지 모델 선정·추가 API 호출은 아직 실행하지 않았다.

## 1. 역할과 모델 분리

| 기능 | 실행 시점 | LLM의 책임 | 코드/검수의 책임 |
|---|---|---|---|
| 챌린지 키워드 후보 | 콘텐츠 제작 도구에서 사전 실행 | 목표 조건에 맞는 후보·오답·조합 초안 | 조건 graph·단어 비용·조합 문법·정답 경로·검수/발행 |
| 유사 이미지 | 콘텐츠 제작 도구에서 사전 실행 | 이미지 모델용 편집 계획·지시, 별도 이미지 모델의 픽셀 생성 | 실제 조건 검수·승인 에셋/variant 등록·커버리지 |
| 업무별 최소비용 추천 | 직접 추천 입력 또는 수정된 개선문 분석 시 | 업무·명시된 제약·필요 기능 추출 | DB 후보 필터·품질 조건·동일 업무량 비용 비교·추천 근거 |
| 프롬프트 개선 | 사용자 요청 시 | 원문 보존 개선안·조건 추가 확장안·변경 설명·팁 | 구조/의미 검증·편집/복사·한도·작업 복구 |

텍스트 모델은 확정한 `gemini-3.1-flash-lite`를 공통 어댑터로 사용하되 기능별 프롬프트·스키마·한도·버전을 분리한다. 추천되는 모델 목록, 챌린지의 저/고성능 등급, 내부 분석 모델은 서로 다른 개념이다.

## 2. 키워드 후보 자동 생성

처리 순서:

1. 제작자가 학습 주제와 목표 조건 초안을 입력하고 권리가 확인된 목표 이미지를 준비한다.
2. 목표 이미지 설명·조건 graph를 추출/작성한다. 이미지 분석을 사용할 때도 대상·개수·색·관계를 운영자가 확정한다.
3. 승인된 조건을 입력으로 LLM이 정답 후보·부분 충족·오지정·충돌 후보를 JSON으로 생성한다.
4. 서버 정책으로 비용을 부여하고 조합 문법/중복/관계 연결/정답 경로를 검사한다.
5. 성공·실패 대표 profile과 결과 이미지가 준비된 버전만 승인 발행한다.

예: 목표가 ‘흰 병 위의 빨간 사과 두 개, 수채화’라면 `사과`, `두 개`, `빨간색`, `흰 병`, `위에서`, `수채화`가 목표 조건을 구성한다. `한 개`, `파란색`, `아래에서`, `사진` 등은 학습할 조건에 맞춘 대안 후보다. 화면에는 기존 UX대로 분류/가격 없이 텍스트 목록으로 표시한다. 내부 entity/condition/conflict 정보는 유지한다.

후보 수는 초기 24~36개 범위를 실험하는 제안이며 확정값이 아니다. 비용/점수/임계값은 LLM이 매번 정하지 않고 콘텐츠 정책에 귀속한다. 선택 시의 자동 문장은 검수한 템플릿 코드로 조합하며 제출마다 LLM을 호출하지 않는다.

초안: `prompts/challenge-keywords.v1.md`.

## 3. 유사 이미지 자동 제작

‘유사’는 시각적 거리보다 학습 조건의 통제된 차이를 뜻한다. 목표 참조 이미지와 변경할 조건을 입력해 편집/변형한다.

| variant 예 | 바꿀 조건 | 검수할 나머지 조건 |
|---|---|---|
| 목표 충족 | 없음 또는 표면적 질감 변화 | 대상·개수·색·관계·스타일 |
| 개수 차이 | 두 개→한 개 | 대상·색·관계·스타일 |
| 속성 차이 | 빨강→파랑 | 대상·개수·관계·스타일 |
| 관계 차이 | 위→옆 | 대상·개수·색·스타일 |
| 스타일 차이 | 수채화→사진풍 | 대상·개수·색·관계 |
| 복합 차이 | 명시된 두 조건 | 나머지 조건이 의도치 않게 변하지 않았는지 |

초기에는 목표 1개당 대표 variant 6~10개부터 검증하되 숫자는 제안이다. 동일 이미지 파일이 여러 허용 profile에 대응할 수는 있지만 핵심 대상/개수/관계가 다른 제출을 임의로 같은 결과에 넣지 않는다. 30개 키워드의 모든 부분집합 이미지를 만들 수 없으므로 동등한 조건 profile로 정규화하고, UI에서 허용하는 선택 공간 전체에 대한 매칭 규칙을 검사한다. 커버리지가 부족하면 후보·제약·문법을 조정하며, 미매칭 시스템 오류를 정상 실패로 소모하지 않는다.

텍스트 LLM은 variant 계획/프롬프트를 만들고 이미지 전용 모델이 실제 에셋을 생성한다. 이미지 편집 모델 후보는 공식 지원 기능·접근·가격·참조 보존을 확인한 뒤 결정한다. 현재 무료 텍스트 키로 이미지 생성까지 가능하다고 가정하지 않는다. 추가 과금이 필요한 제작은 별도 결정 전 실행하지 않으며 검수한 수작업 에셋을 같은 등록 경로로 넣을 수도 있다.

자동 시각 점검은 보조다. 실제 픽셀의 조건과 제작 계획이 다르면 승인하지 않는다. 점수는 선택한 조건·규칙으로 계산하고, 결과 이미지의 실제 조건과 판정 설명이 함께 납득되도록 발행 전 검수한다. 저/고성능 선택은 학습 게임의 모의 정책이며 실시간으로 실제 저가/고가 모델을 비교 호출했다는 뜻이 아니다.

초안: `prompts/image-variants.v1.md`. 모델·제작 옵션·프롬프트·원본/결과 hash·실제 조건·검수자·버전을 보존한다.

## 4. 업무 기반 cost minimization 추천

목표는 ‘품질/기능 조건을 만족하는 검증된 후보 중 가정한 업무량에서 가장 저렴한 모델’이다. 전 세계 모델의 절대 최저가 또는 실제 청구액 보장을 뜻하지 않는다.

### 4.1 분석과 후보 필터

LLM은 요약/번역/추출/작성/코드/추론 등 주요·보조 업무, 언어, JSON/도구/이미지 등 필요 기능, 명시된 제약, 미제공 정보를 추출한다. 모델 이름·가격·적합도·추천 등급을 생성하지 않는다.

서버는 다음을 차례로 확인한다.

1. 활성 모델/endpoint이며 필요한 입력·출력·기능·context를 지원한다.
2. 모델 버전·추론 설정·endpoint의 가격/성능 근거를 정확히 연결할 수 있다.
3. 업무별 품질 기준을 만족한다. 공개 benchmark는 간접 근거이므로 자체 검수 테스트와 함께 정책을 보정한다. 다른 척도 점수를 임의 평균 내지 않는다.
4. 서비스 제한/사용 가능 quota/지연 등 명시된 운영 조건을 만족한다. 무료 가격 0만 보고 실제 사용 불가능한 endpoint를 선정하지 않는다.
5. 비교 가능한 가격 자료가 있고 workload 가정이 정의되어 있다.

자료 부족·조건 충족 후보 없음은 `INSUFFICIENT_EVIDENCE` 또는 `NO_ELIGIBLE_MODEL` 상태로 반환한다. 이것은 사용자의 질문을 못 알아들은 상태와 구분한다.

### 4.2 비용 계산

```text
estimatedCost(m) = assumedInputTokens(m) * inputPricePerToken(m)
                 + assumedBillableOutputTokens(m) * outputPricePerToken(m)
                 + knownApplicableFees(m)
recommended = argmin estimatedCost(m), for eligible m
```

동일 업무/동일 내용과 동일 출력 요구를 비교한다. 실제 토큰화 도구가 있으면 모델별 input 추정치를 사용하고 없으면 버전별 추정 방법을 명시한다. 출력량과 reasoning 과금·캐시·도구/이미지 비용을 확인할 수 없으면 범위를 제한하거나 불확실성을 기록한다. 길고 제공되지 않은 문서를 요약해달라는 한 문장만으로 실제 입력량을 알 수 없으므로 명확한 정책 workload를 쓰거나 필요한 정보를 요청한다.

가상의 계산 예: 동일 업무량 입력 2,000·출력 500토큰, 검증한 두 후보 A/B가 있다고 하자. A의 입력/출력 단가가 각각 $0.20/$0.80 per 1M이면 $0.0008, B가 $0.10/$0.30이면 $0.00035다. 둘 다 품질 기준을 충족하면 B, B가 품질 기준 미달이면 A를 선택한다. 이 숫자는 산식 설명용이며 실모델 단가가 아니다.

동점은 고정된 tie-break(예: 자료 최신성→검증된 지연→stable ID)로 처리한다. Light/Medium/High는 결과 모델의 자체 운영 분류이며 분석 LLM이 자의적으로 붙이지 않는다. 실제 답변을 여러 모델로 생성해 평가하는 호출은 사용자 요청마다 하지 않는다.

### 4.3 저장·UI·수집

기록: taskProfile, textHash, analyzerVersion, snapshotId, policyVersion, workloadAssumptions, eligible/excluded IDs와 이유, 계산 단가·내부 예상비용, selectedModel, evidenceRefs.

UI: 추천 업무·등급·추천 이유, 모델별 실제 단가(100토큰 USD)·관련 지표·출처·갱신일·N/A. 기존 UX대로 요청별 예상 총비용 상자는 넣지 않는다. 근거/업무량 가정은 도움말에서 설명할 수 있다.

OpenRouter/AA는 주간 Actions+수동 실행으로 수집해 검증한 snapshot을 발행한다. API 호출마다 재수집하지 않는다. 공개 표시·재배포 권한과 AA 플랜의 실제 필드를 확인한다. 분석 LLM이 가격을 기억에서 채우지 않는다.

초안: `prompts/task-analysis.v1.md`.

## 5. 프롬프트 개선: 기존 의도와 확장 예시

입력 예: `학교 발표용 재활용 방법 3개 추천좀`.

- 원문 보존 개선안: `학교 발표에 사용할 재활용 방법 3가지를 추천해줘.`
- 확장 예시: `초등학생 대상 학교 발표에 사용할 재활용 방법 3가지를 추천해줘. 각 방법을 준비물과 실천 순서로 나눠 쉬운 말로 설명해줘.`
- 추가 가정: 대상=초등학생, 구성=준비물/실천 순서, 표현=쉬운 말. 모두 원문에 없던 제안임을 명시한다.

한 번의 구조화 요청으로 improvedText, extendedExample, addedAssumptions, changes, tips와 공통 taskProfile을 반환하는 구성을 우선 검증한다. 확장 탭을 여는 동작만으로 재호출하지 않는다. 구조 검증 성공만으로 의미 보존을 보장할 수 없으므로 수량·금지사항·고유명사·언어·목적의 회귀 평가를 별도로 수행한다.

팁은 결과의 실제 구절을 인용하고 서버가 위치를 검증한다. 편집/취소/복사 완료를 구현한다. 추천받기를 누르면 선택한 탭의 최종 문장과 분석 버전을 보낸다. 같은 문장 hash·분석 버전이면 분석 재사용, 수정한 문장이면 새로 분석한다. 초안 분석을 편집된 문장에 그대로 적용하지 않는다.

초안: `prompts/optimizer.v1.md`.

## 6. 공통 요청 처리와 평가

- 사용자 입력은 분석 데이터로 분리한다. 시스템 지시 변경·키/내부 정보 요구가 입력에 있어도 수행하지 않는다.
- 작업 생성과 idempotency 저장→길이/기능별 한도·전체 quota 예약→DB 트랜잭션 밖의 LLM 호출→Zod+의미 검증→저장/사용량 정산 순서다.
- free tier의 전체 프로젝트 quota는 콘텐츠 제작·개선·분석이 공유할 수 있다. 기능별 사용량을 기록하고 온라인 요청용 여유를 남긴다. 무제한 자동 재시도·유료 fallback을 하지 않는다.
- 요청 상태는 DB에 저장한다. 공급자 타임아웃 후 청구/진행 여부를 모르는 작업을 즉시 중복 호출하지 않는다.
- 원문은 필요한 기간만 보관하고 로그에 기본 출력하지 않는다. 키/문서 내부 지시/프롬프트 본문은 CI 로그·공개 artifact로 내보내지 않는다.
- prompt/model/schema/policy/data 버전을 결과에 연결한다. 변경 전 고정 fixture로 회귀 평가한다.

개발용 평가 세트 제안:

| 기능 | 첫 평가 세트 | 검사 |
|---|---|---|
| 키워드 | 서로 다른 목표 10개 | 조건 참조·동의어/충돌·조합 가능·최소 예산 성공·결과 커버리지 |
| 이미지 | 대표 variant 6~10개/목표 | 변경 조건만 바뀌는지, 실제 조건·설명·판정 일관성 |
| 업무 분석/추천 | 업무별 10개씩, 혼합/누락/긴 문서 포함 | 분석 요구 보존·필터·품질 gate·산식·결측·자료 소실 |
| 개선기 | 한국어 50개와 제약/모호성 경계 사례 | 원문 의미 보존·추가 가정 구분·팁 위치·편집 후 재분석 |

수량은 착수 제안이며 테스트를 통과하기 위한 낮은 품질 기준을 의미하지 않는다. 핵심 의미 보존·거래·판정 위반은 출시 전 해결한다.

## 7. 구현 위치와 순서

```text
prompts/                          # 이번에 추가한 버전별 지시 초안
content/challenges/               # 승인 조건·키워드·profile·에셋 manifest (구현 예정)
tools/content/                    # 키워드/이미지 제작·검수·발행 (구현 예정)
apps/api/src/services/llm/         # 공통 Gemini 어댑터·구조 검증 (구현 예정)
```
