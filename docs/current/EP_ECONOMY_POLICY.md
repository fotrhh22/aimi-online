## 챌린지 보상 확인 지급 (2026-11-11, 로컬 구현)

- 보상 금액은 기존 v3 그대로: 기본10 + min(5, floor(성공 제출 후 잔여 게임 예산 × 0.1)). 앞선 시도·힌트·마지막 제출 비용을 반영한 잔여 예산으로 산정하며 EP 잔액과 혼동하지 않는다.
- 새 키워드 퍼즐 성공 제출은 성공/일일 종료와 보상 예정 금액만 저장하고 지갑에 더하지 않는다. 성공 팝업 확인 → POST /v1/attempts/:id/reward에서 지급한다. 최초 성공에만10~15EP 예정되므로 도전별 일일 상한은 그대로다.
- pending/claimed를 소유자의 attempt에 저장. 사용자 잠금·지갑/원장·상태를 같은 repository transaction으로 갱신해 연타·다른 idempotency key·재시작에서도 중복 지급하지 않는다. 클라이언트가 보상 금액을 보내지 않는다.
- 이전 즉시 지급 결과(rewardStatus 없음)는 이미 지급된 것으로 취급하며 다시 지급하지 않는다. 실패 보상은0. 이전 날짜의 미수령 보상도 원래 예정 금액으로 받을 수 있고, 새 날짜 보상을 만든 것이 아니다. earned-day 상한과 실제 수령일의 지갑 증가를 구분한다.
- /v1/state가 날짜와 무관하게 미수령 성공 보상을 반환하여 새로고침·재로그인 후에도 확인 팝업을 복구한다. 저장된 예정 금액은 게임을 다시 하거나 날짜가 바뀌어도 재산정하지 않는다.
- 기존 JSON state 필드 확장으로 별도 DDL 없음. 실제 운영 적용 시 새 API와 프런트를 함께 반영해야 한다. 이번에는 로컬 코드/검증만 수행했고 원격DB·Render 미반영.

## DB와 배포

202611090004_reward_policy_v2.sql은 aimi.reward_policies에aimi-economy-v2(3,1,development_only=false)를 추가한다. 이전 정책과 지갑/원장은 유지한다. API는 새 버전을 명시적으로 선택하며 migration이 빠졌으면 보상을 임의 fallback하지 않는다. 전체 앱의 AIMI_RELEASE_VERSION 게이트·토스 실기기 검증은 별도로 남는다.

원격 적용 순서: 기존 migration/백업 상태 확인→새 migration 적용(`npm run db:migrate`)→최신 API 배포→출석/팁1회·중복·잔액/원장 확인→최신 미니앱 번들 검증. 생성기나 에셋 Storage 이전은 이 정책의 선행 조건이 아니다.

가격의 단일 원본을 에셋 생성기와 API 상품 목록이 공유한다. 에셋 재생성으로 구가격으로 돌아가지 않는다. 신규 에셋은 SHOP_PRICES 등록이 없으면 생성/등록 검증에서 실패한다.
