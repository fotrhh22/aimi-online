# 모델 추천 정책 v4.1 — 업무 분석·제품군·품질 분리

갱신: 2026-11-10. 현재 개발 정책이다. 모델 크기나 실제 업무 품질을 보장하지 않는다.

## 모델군과 LLM 역할

Small=경량·효율형, Medium=균형형, High=상위 수행 능력형 제품군. 업무 난이도, 파라미터 수, 동일 모델의 추론 강도가 아니다. LLM은 taskType, requiredCapabilities, suggestedTier, reason, unknowns를 출력한다. 업무에 충분할 것으로 예상하는 최소 제품군을 제안하며 모델명·가격·점수·개별 모델군은 생성하지 않는다. 실제 시스템 지시는 apps/api/src/services/llm/prompts.ts이고 추천·개선기에 공통 모델군 규칙을 적용한다. 추천은 Gemini.analyze의 TaskSchema 전용 호출이며 개선문을 생성/검증하지 않는다. 기존 분석 캐시는 task-profile-v3 해시로 구분한다.

## 안정적인 모델군 · model-groups-v3

content/policies/model-groups-v3.json의156개명시정책을 model-group-policy.ts로생성하고앱/서버가공유한다. Small32/Medium53/High71이다. 제작사개별/제품군자료로150개를검토했으며이는AIMI의제품포지션해석이다. Meta5개는추가확인제안, NVIDIA Super VL1개는기존정책유지/근거보강으로분리한다. 정책이없는새모델은Medium탐색영역의미검토상태로두고추천근거로쓰지않는다.

모델별정책에는근거URL·보관본문해시·판정이유·검토일·이전등급을기록했다. 가격/현재AA순위/추론강도가바뀌어도제품군은유지한다. 구형상위제품을단지출시세대가오래됐다고Small로낮추지않으므로현재최고성능순위를의미하지않는다. 전체결과는 MODEL_GROUP_REVIEW_RESULTS.md를따른다. 추후모델군정책변경은버전을올린다.

제품군검토와AA매핑검수는별도다. AA참고프로필303개중기존검수매핑10개만실제추천근거로유지한다. 제품군을확정했다고매핑/품질검증완료로승격하지않는다.

## 업무 분석 규칙 보강 · task-profile-v3

단일 변환·요약·추출·짧은 일반 작성/작은 코드 수정은 경량형부터 검토한다. 여러 독립 조건을 충족해 결과를 비교·통합하면 균형형, 많은 단계의 의존·증명·불변식·복합 시스템 설계와 검증이면 상위형을 검토한다. '분석/코드/자세히'라는 단어, 입력 길이, JSON/이미지 기능만으로 승격하지 않는다. 불명확한 조건은unknowns에 기록하고 등급 비율을 강제로 맞추지 않는다.

UI는 Gemini의 최초 suggestedTier와 사용자가 직접 고른 tier를 구분한다. 세부 검증은 RECOMMENDATION_ROUTING_AND_AA_CHART.md를 따른다.

## 품질 gate와 추천

제품군과 품질 검증은 별도다. 검수 AA 매핑·Intelligence Index 버전5·필수 기능·context≥3000·maxOutput≥1000·현재 시점 이후가 아니면서30일 이내인 가격 자료를 확인한다. 일반 업무의 AIMI 프로토타입 최소 점수는 Small5, Medium12, High20이다. 이전 상대 백분위 gate를 대체한다. 이는 AA 공식 기준이 아닌 고정 개발 가정이며 실제 과제 평가로 보정해야 한다. 다른 Index 버전은 재검수 전 추천을 중단한다. 비교 가능한 지표 표본10개 미만이면 근거 부족을 반환한다.

해당 제품군 안에서 적격 후보를 같은 입력2000/출력1000토큰 비용으로 정렬해 최대3개 추천한다. 가격은 제품군이 아닌 정렬에만 사용한다. 적격 모델이 적으면 억지로3개를 채우지 않는다.

AA Coding/Agentic Index는 공식 제공 중단·항상 null이다. 코드 업무에는 종합 점수를 코드 점수로 대체하지 않으며 근거 부족과 이유를 표시한다. 코드 업무 추천까지 검증 완료된 서비스가 아니다. [AA 데이터 점검](../archive/2026-11-development/AA_DATA_AUDIT.md)에 실제 수신 항목·건수·연결 한계를 기록했다.

## 후보와 비용

1. 버전/추론 설정까지 검증된 AA ↔ OpenRouter 매핑.
2. 필수 입력/출력 modality, JSON/도구, context 및 max output 지원 확인. 입력+출력 여유를 포함해 context 검사.
3. 등급별 품질 gate 통과, 가격 비음수·단위 명확, 필요한 부가 요금 계산 가능.
4. 같은 workload에 대한 예상비용 오름차순 정렬. 초기 기본 workload는 입력2000/출력1000토큰(모든 등급 동일)이며 입력 미제공 시 가정임을 기록. 실제 문서 길이가 알려지면 그 값 우선. 모델별 토큰 추정 오차/추론 과금 불확실성이 비교에 중대하면 제외 또는 근거 부족 반환.
5. 동일 모델의 endpoint 중 비교 가능한 가격 하나를 선택하고 canonical model ID 중복 제거 후 최대3개 반환. 자동 provider 라우팅 가격을 고정 endpoint 가격처럼 섞지 않는다. provider별 검증이 부족하면 공개 모델 단위 참고 가격 비교로 범위를 제한한다.
6. 동점: 관련 품질 지표 높은 순 → 비교 가능한 지연 낮은 순 → canonical ID. 다른 설정에서 측정한 지연은 비교하지 않는다.

비용 = 입력토큰×입력단가 + 과금출력토큰×출력단가 + 확인 가능한 부가비용. 0원 endpoint는 한도/가용성 확인이 가능하고 비교 조건을 만족할 때만 포함하며 제한을 표시한다. 적격2개면2개, 0개면 NO_ELIGIBLE_MODEL. 등급을 몰래 낮추지 않는다. top3에 제작사 다양성을 강제하지 않는다.

UI는 모델3개와 추천 이유·등급·입출력100만토큰당 USD·지표·출처·갱신일을 표시한다. 요청별 총비용 상자는 기존 UX대로 추가하지 않는다. 예상비용·workload는 정렬 근거로 서버에 보존하고 도움말에 가정을 설명한다. 가격은 수집 시점 참고값이며 실제 호출/청구 보장은 아니다.
