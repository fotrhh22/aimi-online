# 에셋·챌린지·날짜별 운영 설계

작성: 2026-11-08. 구현 예정 구조다. 콘텐츠 제작과 앱의 실행 경로를 분리하며, 자정에 생성 API나 Actions 성공을 요구하지 않는다.

## 최신 계획 · 2026-11-09

실제 구현 상태와 다음 단계는 CONTENT_STUDIO_IMPLEMENTATION_PLAN.md를 우선한다. 정원 고정 slotId는 폐기하고 자유 배치용 크기/앵커 metadata를 사용한다. 아래 고정 슬롯과 같은 repo apps/content-studio 경로는 과거 제안이다. 현재 권장 계획은 별도 aimi-content-studio 프로젝트와 Supabase 콘텐츠 계약 공유이며 생성기는 아직 구현하지 않았다. 앱의 published 콘텐츠 reader도 별도 구현이 필요하다.

## 최신 범위 변경 · 사용자 결정

별도 콘텐츠 생성기는 사용자가 추후 개발한다. 아래 생성기 구조는 미래 연동 참고이며 이번 앱 구현/출시 목표에 생성기 UI·서버·자동 생성·배포를 요구하지 않는다. 앱에는 승인 데이터 계약·조회·일정 선택을 구현하고, Codex가 PDF를 참고해 대표 상점/캐릭터 에셋과 예시 챌린지 묶음을 직접 준비한다. 사용자 샘플 제공이나 생성기 완성을 기다리지 않는다. 예시도 검수·등록·발행을 구분한다.

챌린지 실행 판정은 서버 조건 매칭 규칙이며 LLM을 호출하지 않는다. 목표/결과 실제 조건과 규칙/키워드 매핑을 함께 검수한다. 상점은 PDF 예시 에셋으로 구현하며 신규 AI 상품/대량 생성은 현재 범위 밖이다. apps/content-studio 폴더도 이번에 생성하지 않는다.

## 파일과 DB의 역할

실제 이미지/스프라이트는 Supabase Storage, DB에는 storage key·hash·종류·크기·버전·검수 상태·조건·일정을 저장한다. 이미지 바이너리를 일반 SQL 행에 넣지 않는다. DB의 asset ID로 소유권/상품/콘텐츠를 연결하고 단기 signed URL을 영구 식별자로 사용하지 않는다.

Storage 논리 경로 제안:

- assets/characters/{characterId}/{version}/: shop-preview, garden-idle, 게임 animation atlas/metadata.
- assets/items/{itemId}/{version}/: thumbnail, transparent garden sprite.
- assets/challenges/{challengeId}/{version}/: target, results/{variantId}.

공개 제공 영역은 승인된 앱 배포 에셋만, 원본/생성 초안/검수 대기 자료는 비공개 영역으로 분리한다. client는 서버가 반환한 승인 manifest만 사용한다. 덮어쓰기 대신 새 버전 경로를 사용한다. 버킷 공개 범위와 캐시 정책은 실제 구성 시 검증한다.

## 상점 에셋 제작

AI 생성은 초안 제작 수단이며 UI 카드 자체를 이미지로 만들지 않는다. 가격·장착 상태·보유 배지는 공통 UI로 그린다.

1. 공통 스타일 가이드: PDF와 맞는 시점·외곽선·광원·색감·그림자·기준 크기.
2. 상품 manifest: itemId, 종류, 가격 정책, 고정 slotId, anchor, 상대 크기, 렌더 순서, preview/sprite assetId.
3. 캐릭터는 상점 썸네일/정원 정지 이미지와 게임 달리기·점프·피격 등 필요한 animation 목록을 분리한다. AI가 독립 생성한 프레임의 일관성을 가정하지 않고 원화 기준 수작업 보정/리깅·프레임 제작을 고려한다.
4. 투명 배경·잘림·테두리/후광·앵커·슬롯 경계·캐릭터 가림을 실제 GardenScene과 게임에서 검수한다.
5. 한 캐릭터와 슬롯별 대표 장식으로 전체 제작 경로를 검증한 뒤 상품 수를 늘린다. 게임 성능/판정은 캐릭터 외형과 분리한다.

정원은 공통 좌표계의 고정 슬롯에 배치한다. 서로 크기가 다른 원본을 단순 width:100%로 표시하지 않고 manifest의 anchor/scale/z-order를 적용한다. 같은 슬롯에는 하나만 장착한다. 카드/편집 화면 위치 라벨 제거와 구매 팝업의 위치 설명은 PDF 규칙을 따른다.

## 챌린지 묶음

하나의 challenge_version은 목표 이미지, 확정 조건 graph, 키워드/충돌/조합 문법, 단어 비용, 모델 등급/임계값, 결과 profile→검수 이미지 매핑, 판정 규칙 버전을 함께 고정한다.

진행: 주제/조건 → 목표 이미지 제작 → 실제 픽셀 검수 → 키워드 후보 → 결과 profile 설계 → 참조 편집/결과 제작 → 조건 검수 → 매핑/최소 예산 성공/허용 조합 커버리지 검사 → 승인.

목표 이미지와 유사 결과는 매번 앱에서 생성하지 않는다. 이미지 생성 전용 모델은 접근·가격·참조 편집 품질을 확인한 뒤 선정하며 확정 텍스트 모델과 분리한다. 초기에는 수작업 묶음으로 기능 구현 가능하다. 대표 결과 6~10개는 실험 시작점일 뿐 모든 선택을 커버한다는 보장이 아니다. 조건상 동등한 조합만 같은 profile로 묶고, 커버리지 부족이면 후보/조합 제약/이미지 수를 조정한다. 미매칭은 시스템 오류이며 정상 오답으로 횟수/예산을 소모하지 않는다.

## 요일 기본 편성과 날짜 발행

요일은 운영자가 편성할 때 쓰는 템플릿, 사용자는 서버가 확정한 한국 날짜별 일정을 조회한다. 매주 고유 이미지를 새로 만들 필요는 없다. 승인 묶음을 재사용하거나 충분한 재고가 있을 때 교체한다. 재사용/중복 허용 기준을 편성 설정으로 둔다.

개발용 7일 예: 월 Dino+A, 화 길건너기+B, 수 러너+C, 목 Dino+D, 금 길건너기+E, 토 러너+F, 일 Dino+G. 게임은3종이므로 한 주에 반복이 생기며 월요일도 다음 주에 같은 게임이어야 할 의무는 없다. 이는 예시 편성으로 운영 확정 아님.

핵심 DB 구조 제안:

- assets / asset_versions: 파일·출처·hash·제작 정보·검수 상태.
- item_catalog / character_definitions: 상품과 에셋 버전·슬롯/animation 정의.
- challenge_versions / result_variants: 목표·조건·키워드·이미지 매핑.
- game_versions: 종류·시뮬레이션·점수/예산 정책 버전.
- schedule_releases: 승인 일정 묶음과 발행 상태.
- daily_missions: local_date 유일, game_version_id, challenge_version_id, economy/rule version, release_id.

발행 흐름:

1. 초기 7일치+검수 fallback을 확보하고 이후 14~28일치 재고 확보를 운영 목표로 삼는다. 수량은 제안이다.
2. CLI에서 누락 파일/조건·미승인 버전·예산 경로·날짜 중복·지원되지 않는 게임 코드 여부 검사.
3. 파일 업로드와 무결성 확인 완료 → DB 초안 등록 → 검수 승인 → 트랜잭션으로 일정 발행. Storage/DB를 하나의 원자 거래라고 가정하지 않는다. 실패 초안은 노출하지 않고 나중에 정리한다.
4. GET /missions/today가 Asia/Seoul 서버 날짜로 발행 일정을 선택. 자정 스케줄러 없이 조회 시 전환된다.
5. 당일 최초 해석한 일정 버전을 날짜별로 고정하고 이후 누락분을 채웠다고 진행자마다 다른 과제를 주지 않는다. 예정 일정이 없으면 검수 fallback을 그 날짜에 원자적으로 고정한다. fallback도 없으면 점검 상태로 시작을 막고 횟수를 차감하지 않는다.
6. play/attempt는 시작 당시 버전과 날짜를 저장. 자정·콘텐츠 교체 뒤에도 원래 결과 재현. 당일 긴급 중단은 신규 시작 차단·기존 세션 처리 정책으로 명시한다.
7. 롤백은 신규 조회용 release 전환이며 이미 시작한 세션/결과 기록을 재작성하지 않는다. 참조 중인 파일·버전은 삭제하지 않는다.

## 도구와 자동화의 경계

우선 content/challenges, content/catalog, content/schedules manifest와 tools/content 검사/업로드/발행 CLI를 구현한다. 별도 대형 관리자 웹을 먼저 만들 필요는 없다. 생성 명령과 발행 명령은 분리하고 생성 성공만으로 승인하지 않는다. 공개 저장소에 비밀·비공개 생성 원본을 커밋하지 않는다.

GitHub Actions: 기존 build/test + 모델 자료 주간/수동 수집 + 승인 콘텐츠 검사/수동 발행 + 미래 일정 부족 점검. 이미지 생성은 수동 또는 제한된 제작 배치로 시작한다. 매일 00시 생성→즉시 배포하는 의존은 만들지 않는다. 모델 수집은 정상 스냅샷 발행, 콘텐츠는 정상 release 발행이라는 별도 경로다.

## 출시 전 검증

에셋 누락·구버전 캐시·업로드 중단·동시 발행·일정 없음·서버 재시작·23:59 시작/00:00 제출·결과 재조회·비공개 초안 접근·보유품/이미지 버전 일치·조합 미매칭 복원을 검증한다. 최초 앱 진입에 전체 날짜/전체 상품 원본을 선다운로드하지 않고 당일 콘텐츠와 보이는 상품을 우선 로드한다.

## 별도 콘텐츠 생성기 · 사용자 결정 반영

키워드·목표/유사 이미지 생성과 검수는 사용자 미니앱과 분리한 운영 전용 생성기에서 수행한다. 별도 실행/배포 단위로 두며 같은 Supabase 프로젝트의 DB와 Storage를 공유한다. 별도 Git 저장소는 필수가 아니므로 우선 같은 repo의 apps/content-studio(신규 예정)로 관리하고, 배포/의존성/환경변수는 miniapp과 분리한다. 자동으로 miniapp 번들에 포함하지 않는다. 별도 repo가 필요해지면 계약 패키지 버전 관리 후 분리 가능하다.

생성기 흐름: 운영자 주제/조건 → 목표 이미지 초안 → 실제 조건 확정 → 키워드/결과 profile 초안 → 참조 기반 유사 이미지 → 개별 수정/재생성 → 검수 → 날짜별 편성 → 발행. 상점 에셋은 동일 도구의 별도 제작 유형으로 처리할 수 있으나 캐릭터 animation 보정은 별도 제작 절차다.

공유 계약은 asset/challenge/schema version과 승인 release다. 초안 수정은 운영 전용 staging, 앱 API는 published만 조회한다. 정답/평가 내부 테이블을 미니앱에서 직접 읽지 않으며 앱 API가 필요한 공개 데이터만 반환하고 판정한다. 생성기가 앱의 사용자/지갑/원장을 수정하지 않도록 DB 역할을 분리한다. 생성·검수·발행 권한과 운영자 인증을 갖추고 DB migration 소유자는 한 경로로 통일한다. 생성기 서버만 이미지/LLM 키를 보유하며 브라우저에 관리자 키를 넣지 않는다.

발행은 파일 무결성/조합 커버리지/정답 경로 검증 후 수행한다. 생성기 중단·API quota 소진에도 이미 발행한 날짜별 콘텐츠로 앱은 계속 동작한다. 별도 생성기가 매 플레이마다 호출되거나 자정 실행을 기다리는 연결은 만들지 않는다. 생성기 서비스/DB 역할은 이번 설계에서 생성하지 않았다.
